# Оформление delivery issue

Issue определяет один проверяемый результат, а не хранит обсуждение вариантов.
Сначала применить owning skill предметной области: он определяет архитектурное
содержание, этот skill — форму и полноту задачи.

## Собрать authority

До написания issue:

- прочитать `AGENTS.md`, `docs/launch/README.md`, применимый канонический root,
  принятые ADR и документы владельца;
- проверить фактический код, конфигурацию и открытые predecessor/successor issues;
- зафиксировать bounded-context owner, writer данных, trust surface, входной
  handoff, выходной handoff и непосредственного потребителя результата;
- брать версии из `config/toolchain-versions.json`, несекретные параметры из
  `config/platform.yaml`, а секреты — только через scoped materialization из
  `secrets/platform.secrets.sops.yaml`.

Если архитектурное решение ещё не принято, не маскировать выбор вариантами в
delivery issue. Сначала закрепить решение в владеющем документе; до этого задача
не готова к реализации.

## Ограничить результат

- Один issue — один независимо принимаемый результат и один основной владелец.
- Не смешивать разные сервисы, владельцев, cleanup и будущую инфраструктуру.
- Если части имеют разные handoff или могут приниматься отдельно, оформить
  отдельные связанные issues до публикации.
- Не добавлять compatibility path, abstraction, dependency или заготовку без
  прямого acceptance requirement текущей задачи.
- Заменяемый путь удалить в том же issue, если владеющий документ не требует
  периода совместимости.

## Построить body

Соблюдать этот порядок. Пропускать можно только неприменимые предметные
подразделы внутри блока реализации, но не основные разделы.
Все проверяемые требования, кроме итогового критерия готовности, оформлять
неснятыми `- [ ]` checkboxes.

### `# Результат`

Одним абзацем назвать наблюдаемое состояние после merge. Не описывать процесс и
не обещать будущие возможности.

### `## Место в единой линии`

Checkboxes должны назвать:

- predecessor и обязательное состояние его handoff;
- точные входы, которыми пользуется задача;
- точный выход и его владельца;
- непосредственные successor issues и условие их разблокировки.

### `## Неприкосновенные границы`

Зафиксировать владельцев данных, разрешённых writers, trust boundaries,
транзакционные границы и запрещённые межвладельческие связи. Не повторять общие
правила репозитория, если они не являются риском именно этой задачи.

### `## Что создать и изменить`

Разбить реализацию на предметные подразделы и перечислить только обязательные
изменения. Для каждого применимого изменения указать точный package/service,
путь, API surface, command/event, schema/migration, config key, secret reference,
deadline/limit, idempotency/error semantics и удаляемый старый путь. Ссылаться на
владеющий контракт вместо копирования изменяемого реестра значений.

### `## Обязательные тесты`

Каждый checkbox должен защищать конкретный acceptance criterion или риск
регрессии. Указать самый узкий существующий test target. Новый test file или
test infrastructure разрешён только когда существующий target не покрывает
изменяемое поведение.

### `## Обязательные команды`

Перечислить только реально существующие локальные команды либо команды, которые
сама задача обязана создать. Не дублировать одну и ту же проверку под разными
именами.

### `## Документация и handoff`

Назвать изменяемый владеющий документ, точный выход для successor и способ
проверить, что consumer использует этот выход без второго источника истины.

### `## Границы задачи`

Явно перечислить близкие, но исключённые изменения: чужие bounded contexts,
будущие capabilities, миграцию legacy-кода, альтернативные реализации и
несвязанный cleanup.

### `## Ветка и PR`

Указать одну ветку от актуальной `develop` по соглашению `AGENTS.md`, один issue
и один PR в `develop`. Название, body и изменяемая документация — на русском.

### `## Критерий готовности`

Одним коротким утверждением связать наблюдаемый результат, обязательные проверки,
handoff и отсутствие запрещённых путей.

## Писать проверяемые checkboxes

Каждый checkbox обязан:

- проверять один факт по коду, diff, тесту, документу или состоянию GitHub;
- начинаться с конкретного действия или результата;
- называть точный artifact, owner, path, contract или authority значения;
- не содержать «рассмотреть», «при необходимости», «выбрать», `X или Y`;
- не дублировать гарантию из другого раздела;
- оставаться снятым до появления проверяемого доказательства.

Не ставить checkbox на чтение документа или размышление без создаваемого
artifact. Не подменять критерий готовности количеством выполненных действий.

## Проверить перед публикацией

- Нет второго issue с тем же результатом.
- Predecessor, successor, owner и handoff совпадают с фактической delivery line.
- Все ссылки ведут прямо на определяющие документы и связанные issues.
- Указаны только существующие labels; новые labels не придумываются.
- Body не оставляет исполнителю архитектурного выбора.
- Каждый пункт необходим для результата, а каждый обязательный результат покрыт.

Создание или изменение issue и labels на GitHub выполнять только после явного
разрешения пользователя и проверки `origin` и `gh repo view`. После реализации
передать задачу `issue-delivery-closure`; этот skill сам issue не закрывает.
