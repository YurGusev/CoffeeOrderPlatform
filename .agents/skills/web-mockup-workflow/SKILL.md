# Проработка макетов сайта

Локальный workflow: бриф → DESIGN.md → три интерактивных варианта → сравнение →
браузерные доказательства → выбор пользователя. Результат — пакет для обсуждения,
не production UI. Figma, Canva, MCP, облачная публикация и новые зависимости не нужны.
Это процедурный навык для агента, не фоновый плагин и не исполняемый автозапуск.

## Когда использовать

- «Сделай макеты сайта», «покажи три направления», «проработай экран»,
  «сравни варианты интерфейса», «web-mockup-workflow».
- При доработке выбранного варианта продолжать его, не генерировать ещё три.
- Для исправления production-компонента без запроса макетов использовать
  `react-operator-frontend`, а не создавать отдельную реализацию.

## Подготовка и подключение навыков

Работать от корня текущего проекта; проверить `git status` через `terminal`.
Не перезаписывать пользовательские изменения и существующие пакеты макетов.
В Hermes загружать следующие навыки через `skill_view(name="...")` по этапам;
это обязательные зависимости workflow, а не повод копировать их в репозиторий:

| Этап | Навык | Что использовать |
|---|---|---|
| Бриф | `omh-frontend` | Аудитория, главное действие, карта страниц и состояний; только подготовка, не доказательство исполнения |
| Композиция | `claude-design` | Тип поверхности, иерархия, осмысленные различия и устранение шаблонного оформления |
| Референсы | `popular-web-designs` | Выбор визуальных принципов; открыть только нужные `templates/<site>.md` через `skill_view` |
| Контракт | `design-md` | YAML-токены, ссылки токенов и структура DESIGN.md |
| Варианты | `sketch` | Три самостоятельных кликабельных HTML-макета и их компромиссы |
| Проверка | `web-surface-verification` | Проверка реально открытой страницы, состояний, viewport и очистки процессов |

Не вызывать инструменты из примеров навыков, пока их наличие не подтверждено.
Если зависимость не загружается, сообщить её имя и незавершённый этап;
не устанавливать её автоматически и не объявлять полный workflow выполненным.
Если проектный навык не найден, проверить точный cwd, доверие и discovery;
после исправления нужна новая сессия, а не глобальная копия навыка.

## Процедура

### 1. Зафиксировать бриф и границы

Прочитать релевантные UI-файлы, стили, токены, supplied-референсы и `package.json`.
Для интерфейса CoffeeOrderPlatform прочитать `docs/launch/07_FRONTEND_CONTRACT.md`
и загрузить `react-operator-frontend`. Не выдумывать бизнес-действия: server state,
`allowedActions` и UnknownOutcome сохраняют смысл даже в демонстрации.

Записать в README пакета: аудиторию, страницу/сценарий, главное действие, контент,
ограничения, источники и явно отмеченные допущения. Уточнять только то, что меняет
результат; не повторять вопросы, на которые пользователь уже ответил.
Не расширять набор страниц ради наполнения макета.

### 2. Определить композицию и DESIGN.md до HTML

Выбрать основной тип поверхности: наблюдение, операции, сравнение, настройка,
изучение, каталог или инспектор. Не превращать операционный экран в landing hero.
Выбрать три направления с описательными slug, например `compact-table`,
`split-inspector`, `guided-list`; различать композицию, плотность или взаимодействие,
а не только палитру. Главное действие, исходный контент и состояния у них одинаковы.

Создать `sketches/<brief-slug>/DESIGN.md`, не заменяя корневую дизайн-систему.
Использовать YAML-токены `name`, `colors`, `typography`, `spacing`, `rounded`,
`components` по `design-md`; текст и обоснования писать по-русски. Допускаются
канонические технические заголовки формата. Указать источник существующих токенов,
иерархию, размеры, контраст, focus, reduced-motion и адаптивное поведение.
Общие токены едины; разрешённые различия направлений описать отдельно в Layout.
Не создавать три конкурирующих источника бизнес- или дизайн-истины.

Взять из референсов принципы, не копировать логотипы, фирменные тексты и ассеты.
Сначала существующие локальные ресурсы; осознанный системный шрифт допустим.
Не запускать предлагаемые сторонними навыками `npx`-установки, CDN, туннели,
экспорт Tailwind/DTCG или плагины без отдельной необходимости и разрешения.
Если официальный design-md CLI уже доступен, выполнить lint; иначе проверить
YAML и ссылки доступными средствами, явно отметив отсутствие официального lint.

### 3. Построить ровно три варианта

Создать пакет по [шаблону результата](templates/result.md).
Каждый `variants/<stance>/index.html` — открываемый локально HTML с inline CSS/JS,
без сборки, сетевых запросов, аналитики, API-вызовов и настоящих мутаций.
Встроить CSS custom properties из DESIGN.md; не добавлять runtime/config layer.
Демонстрационные данные и имитацию действий обозначить как демонстрацию;
не выдавать их за реальные заказы, цены или бизнес-результаты.

Главное действие должно давать видимый результат. Сделать доступные pointer/keyboard
пути, hover/focus и хотя бы один содержательный переход состояния у каждого варианта.
Включить только согласованные loading/empty/error/disabled/validation состояния;
не добавлять нерелевантные сценарии. Для русского интерфейса использовать `lang="ru"`,
реалистичные подписи и длинный текст для проверки переносов.
Записать для каждого направления сильные стороны, ограничения и ожидаемую аудиторию.

### 4. Проверить варианты, а не только их исходники

До запуска определить матрицу: вариант × страница × согласованное состояние × viewport.
Минимум для каждого варианта: `1440×900`, `768×1024`, `375×812`, `deviceScaleFactor: 1`.
На одной странице initial-state даёт девять PNG; дополнительные состояния увеличивают
матрицу. Не называть базовые девять снимков полным покрытием остальных состояний.

Загрузить `web-surface-verification`. Для standalone HTML разрешён локальный
loopback-only static server с корнем в пакете; использовать существующий runner,
либо стандартный `python3 -m http.server --bind 127.0.0.1 --directory <package> <port>`
через `terminal`. Проверить HTTP-ответ до браузера. Для собранного приложения
использовать только предусмотренный проектом build/preview, не заменять его этим сервером.
Использовать установленный Playwright или доступный браузерный инструмент;
не устанавливать браузер и test infrastructure без разрешения.

Открывать изолированный browser context для каждой линии проверки. Дождаться шрифтов
и устойчивого состояния, выполнить сценарий, сохранить full-page PNG и наблюдения.
Для каждого снимка записать URL, viewport, состояние, путь и SHA-256 исходного HTML,
время захвата, браузер/version, SHA-256 PNG и команды/шаги воспроизведения.
Хеши и время получать инструментом, а не заполнять предположениями.

Проверить переполнение, обрезание/наложение текста, шрифты, контраст, размеры целей,
главное действие, Tab/Enter, фокус и Escape/возврат фокуса при наличии модального окна.
Записать console errors, failed responses и неожиданные внешние запросы.
Axe запускать только если уже доступен; отсутствие axe указать отдельно и не заменять
его утверждением о полной WCAG-сертификации. Автотест, ручная проверка клавиатуры
и визуальный просмотр — отдельные факты.

Просмотреть реальные PNG доступным инструментом с поддержкой изображений и сравнить
с DESIGN.md/референсом. Сам факт создания PNG не доказывает визуальное качество.
Если просмотр недоступен, выдать снимки для просмотра пользователем со статусом
«визуально не проверено». Не придумывать отсутствие дефектов.
Исправлять наблюдаемые дефекты и переснимать затронутые строки после последней правки.
При блокере или исчерпании согласованного бюджета итераций перечислить остаток,
а не заявлять успех. Закрыть contexts/server в finally и проверить освобождение порта.

### 5. Сравнить и передать на выбор

Заполнить README по шаблону: три ссылки, таблица сравнения, рекомендация с причинами,
сводка проверок и ограничения. Не выдумывать численные оценки или победу в UX-тесте.
Показать ключевые снимки и HTML через `MEDIA:/absolute/path`; preview в Hermes —
дополнительный способ просмотра, не замена viewport-проверке.

Остановиться на выборе направления пользователем. Перенос в React, изменение API,
схем и production-файлов — отдельная согласованная задача.
Если выбор уже сделан, обновлять только выбранный вариант, DESIGN.md при необходимости
и его доказательства; не удалять остальные пользовательские файлы автоматически.

## Критерий завершения и ограничения

- DESIGN.md существует до HTML и соответствует фактическим токенам вариантов.
- Есть три работающих варианта, таблица сравнения и обоснованная рекомендация.
- Каждая строка матрицы имеет свежие снимок и наблюдения либо явный blocker.
- Статус «проверено» допустим только для реально выполненных проверок без
  необъяснённых ошибок; недоступный browser/vision оставляет пакет непроверенным.
- Доказательства относятся к макетам, а не production, field performance или одобрению UX.
- Итог перечисляет пути, точные команды, результаты и то, что ещё не проверено.
- Никаких изменений глобальных навыков, секретов, публикаций или коммитов по умолчанию.
