# Оркестратор Astra и Luna

Адаптировано из [codex-astra-luna-orchestrator](https://github.com/donvito/codex-astra-luna-orchestrator).
Настройки и запуск: [инструкция проекта](../../../.codex/README.md).

Astra владеет декомпозицией, решениями, интеграцией и итоговой проверкой.
Делегируй только независимую ограниченную часть, пока у родителя есть полезная
работа. Не запускай агентов ради заполнения лимита. Зависимые шаги выполняй
последовательно. Простые задачи решай самостоятельно.

- `explorer`: найти файлы, проследить поток и существующие тесты; только чтение.
- `worker`: реализовать согласованный scope на Luna.
- `tester`: выполнить проверки; менять тесты только по поручению.
- `researcher`: проверить актуальные факты по первичным источникам; только чтение.
- `reviewer`: независимое ревью на Astra; только чтение.

Передавай цель, точные границы владения файлами, необходимый контекст,
ограничения, критерии готовности и ожидаемый результат. Предупреждай worker,
что он работает не один и должен сохранять чужие изменения. Не назначай
пересекающиеся файлы параллельным исполнителям.

Используй настроенные роли без явного переопределения модели и reasoning:
Luna наследует high в большом режиме и medium в экономичном. Не повышай модель
исполнителя без прямого запроса. Глобальные роли других провайдеров не входят
в эту схему. Субагенты не расширяют scope и не делегируют дальше.

Применяй предметные навыки через coffee-platform-router. Соблюдай AGENTS.md
и выданные пользователем разрешения: этот навык не разрешает внешние записи.
Родитель проверяет diff, результаты обязательных проверок и существенные
замечания reviewer; сообщает результат и непроверенное поведение.

## Цикл ревью и исправлений

После реализации tester проверяет поведение, затем reviewer проверяет diff.
Reviewer возвращает результат корневому Astra, а не запускает исполнителей сам.
Для каждого замечания он указывает стабильный идентификатор, приоритет,
файл и строку или символ, проблему и последствия, рекомендуемую роль
и конкретную проверку для приёмки исправления.

Root разбирает замечания и назначает только необходимые роли:
- worker исправляет подтверждённую ошибку;
- explorer прослеживает код и область влияния, если причина ещё не установлена;
- researcher уточняет контракт или документацию, если не хватает фактов.

Исследование, от которого зависит исправление, выполняется до worker.
Независимые замечания можно обрабатывать параллельно в пределах общего лимита
и без пересечения файлов. Root передаёт идентификаторы замечаний и критерии
приёмки, переиспользует доступных исполнителей и собирает результаты.

После исправлений tester выполняет релевантные проверки; reviewer повторно
проверяет прежние замечания и новый diff на регрессии. Для каждого прежнего
замечания reviewer сообщает: устранено, осталось или опровергнуто с доказательством.
Успешные тесты сами по себе не закрывают замечание.

Пока остаются подтверждённые существенные замечания, root повторяет цикл.
Если цикл не даёт прогресса, root разбирает причину и меняет подход; вопрос
пользователю нужен только для решения, которое нельзя принять в рамках scope.
После завершения reviewer root интегрирует результат и проверяет обязательные
критерии готовности. Merge PR и закрытие issue выполняет только root по
issue-delivery-closure и при явном разрешении пользователя; этот цикл такого
разрешения не добавляет. Простые задачи не требуют запуска всех ролей.
