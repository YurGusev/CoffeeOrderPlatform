# Роли и цикл Codex

Этот раздел применяется только в Codex. В Hermes используются `delegate_task`
и правила основного SKILL.md; роли и reasoning из `.codex` туда не переносятся.
Настройки: [инструкция проекта](../../../../.codex/README.md).

## Схема исполнения

Схема ниже применяется при выборе Astra корневой моделью. Модель root и
reasoning выбирает пользователь; проект их не переопределяет. При запуске
на Luna root остаётся Luna, автоматической передачи root к Astra нет.
Дочерние роли сохраняют закреплённые модели независимо от выбора root.

```text
                  GPT-6 Astra
               root / orchestrator
                       |
       +---------------+---------------+
       |               |               |
    explorer         worker        researcher
      Luna            Luna            Luna
       +---------------+---------------+
                       |
                     tester
                      Luna
                       |
                    reviewer
                     Astra
                       |
                  GPT-6 Astra
               integrate + verify
```

Все субагенты запускаются root; стрелки означают передачу результатов через
root, а не вложенное делегирование. Researcher передаёт подтверждённые факты
root и нужным исполнителям. Tester получает итог реализации и критерии;
reviewer — итоговый diff и результаты tester. Независимый reviewer не заменяет
финальную проверку root. Применять эту цепочку для сложной делегированной
разработки; запускать только роли, для которых есть содержательная подзадача.

## Роли

- `explorer`: найти файлы, проследить поток и существующие тесты; только чтение.
- `worker`: реализовать согласованный scope на Luna.
- `tester`: выполнить проверки; менять тесты только по поручению.
- `researcher`: проверить актуальные факты по первичным источникам; только чтение.
- `reviewer`: независимое ревью на Astra; только чтение.

Передавать цель, границы владения файлами, необходимый контекст, ограничения,
критерии готовности и ожидаемый результат. Worker сохраняет чужие изменения;
параллельные исполнители не меняют пересекающиеся файлы.

Использовать настроенные роли без явного переопределения модели и reasoning:
Luna наследует high в большом режиме и medium в экономичном. Не повышать модель
исполнителя без прямого запроса. Глобальные роли других провайдеров не входят
в эту схему. Субагенты не расширяют scope и не делегируют дальше.

## Границы и экономия Astra

По умолчанию экономим контекст и работу Astra, передавая содержательные
исполнительские подзадачи Luna. Не ждать, пока root сам завершит исследование.

| Работа | Владелец |
|---|---|
| Цель пользователя, scope, acceptance, архитектурные решения, разрешения | root Astra |
| Поиск в незнакомой области, трассировка нескольких модулей, карта callers/tests | explorer Luna |
| Внешняя документация, сравнение подтверждённых контрактов и версий | researcher Luna |
| Реализация и исправления в назначенных файлах, включая документацию | worker Luna |
| Запуск проверок, воспроизведение ошибок и разбор длинного вывода | tester Luna |
| Независимое ревью содержательного изменения кода после тестов | reviewer Astra |
| Приёмка доказательств, разрешение противоречий, итоговая интеграция | root Astra |

Первичная проверка root: понять запрос, посмотреть состояние ветки/рабочего
дерева, выбрать навык и прочитать определяющий контракт или известный entrypoint.
Если дальше нужен поиск по подсистеме, чтение нескольких реализаций или длинных
логов, выделить ограниченную задачу Luna до этого чтения. Пока Luna работает,
root уточняет критерии, проверяет смежный контракт или независимую часть задачи.
Не придумывать параллельную работу ради делегирования: если полезной независимой
части для root нет, выполнить задачу напрямую. Зависимые этапы не запускать
параллельно; worker получает результаты необходимого исследования.

Прямое выполнение root: короткий ответ, git status, одна известная настройка,
чтение конкретного небольшого фрагмента или простая локальная правка. Такие
действия не требуют полной цепочки ролей. Недоступность субагентов сообщить;
не имитировать делегирование и продолжать разрешённую работу локально.

Для экономии контекста передавать Luna самостоятельное задание с путями,
scope и acceptance, без полной истории беседы, когда инструмент это позволяет.
Просить краткий результат: вывод, точные пути/символы, команды и результаты,
неопределённости. Полные логи возвращать только для конкретного сбоя; секреты
не включать. Переиспользовать исполнителя для уточнений вместо нового запуска.

Root читает участки, определяющие архитектуру, безопасность и подтверждённые
замечания; не повторяет полный поиск explorer, тестовый прогон tester или всё
ревью reviewer. Дополнительная проверка нужна при новом diff, сбое, пробеле или
противоречии в доказательствах. Обязательные acceptance gates не сокращаются.
Reviewer получает конкретный итоговый diff и результаты tester, а при повторе —
изменения после ревью и прежние finding IDs. Не запускать reviewer до готовности
результата, кроме явного запроса пользователя на промежуточное ревью.

## Цикл ревью и исправлений

После реализации tester проверяет поведение, затем reviewer проверяет diff.
Reviewer возвращает результат корневому Astra, а не запускает исполнителей сам.
Для каждого замечания указывает стабильный идентификатор, приоритет, файл и
строку или символ, проблему, последствия, рекомендуемую роль и проверку приёмки.

Root разбирает замечания и назначает только необходимые роли:
- worker исправляет подтверждённую ошибку;
- explorer прослеживает код и область влияния, если причина ещё не установлена;
- researcher уточняет контракт или документацию, если не хватает фактов.

Исследование, от которого зависит исправление, выполняется до worker.
Независимые замечания можно обрабатывать параллельно в пределах общего лимита
и без пересечения файлов. Root передаёт идентификаторы замечаний и критерии
приёмки, переиспользует доступных исполнителей и собирает результаты.

После исправлений tester выполняет релевантные проверки; reviewer повторно
проверяет прежние замечания и новый diff на регрессии. Для каждого замечания
сообщает: устранено, осталось или опровергнуто с доказательством.
Успешные тесты сами по себе не закрывают замечание.

Пока остаются подтверждённые существенные замечания, root повторяет цикл.
Если цикл не даёт прогресса, root разбирает причину и меняет подход; вопрос
пользователю нужен только для решения за пределами scope. После ревью root
интегрирует результат и проверяет обязательные критерии готовности. Merge PR
и закрытие issue выполняет только root по issue-delivery-closure и при явном
разрешении пользователя; этот цикл разрешения не добавляет. Простые задачи
не требуют запуска всех ролей.
