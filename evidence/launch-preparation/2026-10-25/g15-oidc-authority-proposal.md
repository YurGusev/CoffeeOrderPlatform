# Предложение authority для G15 и OIDC

Статус: предложение для решения владельца; ни один вариант ниже не одобрен этим документом и не реализован. Проверка исходников выполнена 25 октября 2026 года. Рабочее дерево содержит параллельные изменения, поэтому перечисленное состояние не является чистым кандидатом или доказательством gate.

## Что требует G15

`docs/launch/21_LAUNCH_VERIFICATION_SPEC.md` определяет G15 как `pnpm test:playwright`: проходят Chromium-сценарии критического пути, accessibility, deep link, конфликтов и realtime. Связанные требования #13 и #119 включают browser session, восстановление после reload, реальные эффекты владельцев, SSE, deep links/assets/API fallback, запрет внутренних/provider routes и fail-closed авторизацию на ingress.

Текущий `apps/web/test/operator-flow.spec.ts` запускает Vite preview и перехватывает через `page.route` `/auth/session`, logout, client API и `/events`; эти тесты проверяют UX, но сами по себе не доказывают OIDC или реальные owner effects. `tests/nginx/cutover.test.mjs --web-served-proof` проверяет SPA за nginx, но его browser flows также используют маршрутизационные mocks, а owner DTO подменяются. В `verification/launch/v1/run.mjs` G15 поэтому сейчас fail-closed: context-bound producer integrated ingress/owner browser receipt отсутствует. Для G15 нужны настоящий браузер и ingress/runtime, а не только существующий mocked Playwright suite.

Нормативное требование не называет обязательным именно production IdP. `docs/launch/29_NGINX_TRANSPORT_AND_AUTH.md` отдельно фиксирует, что production login остаётся NOT_RUN, пока нет действительного provider profile/evidence. Следовательно G15 может доказать браузерную интеграцию с изолированным test identity, если владелец отдельно разрешит такой профиль и receipt явно ограничит выводы; production login и реальная идентичность от этого не становятся PASS.

## Текущее OIDC-положение

В `config/platform.yaml` `browserOidc: null`; `apps/edge-gateway/src/index.ts` при null выбирает fail-closed adapters. Закрытая схема `config/platform.schema.json::$defs.browserOidcProfile` требует ровно `issuer`, `clientId`, `authorizationUrl`, `tokenUrl`, `jwksUrl`, `redirectUri`, `allowedAlgorithms: ["RS256"]`, `actorRefClaim`, `permissionsClaim`. Composition сверяет callback с `${platform.publicBaseUrl.origin}/auth/callback`.

В каталоге сервисов Edge ссылается на `edge.oidcClientSecret`, а `edge.tlsCaBundle` объявлен optional; наличие client secret не создаёт OIDC profile. Секретные значения здесь не читались и в proposal не приводятся. Реальная регистрация issuer/client/claims сейчас не указана. Документ [#159 transport/auth](../../../docs/launch/29_NGINX_TRANSPORT_AND_AUTH.md) также говорит, что текущий config не содержит этих provider inputs.

В существующих realtime fixtures уже есть синтетический authorization-code + PKCE + RSA/JWKS identity provider (`tests/realtime/fixtures/setup.mjs`, `tests/realtime/fixtures/services.mjs`): issuer `https://idp.fixture.invalid`, endpoints `/authorize`, `/token`, `/keys`, client `issue12-fixture`, claim names `actor_ref` и `permissions`, RS256 и callback от fixture `publicBaseUrl`. Сертификат IdP создаётся с SAN `DNS:idp.fixture.invalid`; Edge получает CA через scoped `NODE_EXTRA_CA_CERTS=/fixture/certs/ca.crt`. Это тестовая fixture, а не внешний issuer. Её текущая изолированная сеть не даёт автоматически разрешённого DNS/маршрута из host Chromium к `idp.fixture.invalid`; интеграционный harness должен решить это внутри собственного изолированного network namespace и проверить TLS/SAN. Недопустимы `ignoreHTTPSErrors`, отключение проверки сертификатов, `/etc/hosts`-изменение хоста или общий host-network workaround. `edge.tlsCaBundle` нельзя считать автоматически подключённым к OIDC fetch: существующий fixture явно устанавливает Node CA locator для Edge. Текущая fixture создаёт private-key файлы в обычном временном каталоге; это не одобряет их использование как runtime materialization. Публичный CA certificate для TLS проверки должен быть доверен и в disposable Chromium browser profile, и в Edge; в браузер передаётся только сертификат, без CA private key и без изменения host trust store. Проверки должны включать успешную цепочку с ожидаемым SAN и отказ для неверного CA/SAN, сохраняя стандартную TLS hostname verification.

## Вариант A — реальный issuer для постоянной runtime-конфигурации

Источник значений — конкретная регистрация приложения у выбранного владельцем IdP и его опубликованные metadata/JWKS endpoints. До реализации владелец должен предоставить или одобрить только URI/идентификаторы (не пароли): issuer, client ID, authorization/token/JWKS endpoints, точный redirect URI, RS256 и mapping subject/permissions claims. Redirect обязан совпадать с публичным origin из `platform.publicBaseUrl` и `/auth/callback`. Нужны подтверждённые provider-side регистрации redirect URI, client type и claim policy; если провайдер требует confidential client credential, он передаётся только через существующую scoped SOPS materialization Edge. Нельзя придумывать tenant/account/URL или читать/публиковать секрет.

Предполагаемые файлы и границы: `config/platform.yaml` получает только утверждённый `browserOidc` объект; `config/platform.schema.json` уже описывает его форму, поэтому расширение схемы не нужно. `secrets/platform-secrets.schema.json` и `config/service-catalog.json` уже описывают Edge secret scope; изменять их можно лишь если подтверждённая модель провайдера требует нового типа секрета. `apps/edge-gateway` и nginx не должны получать общий CA bypass или новый публичный endpoint. Внешние side effects — создание/изменение IdP app registration, redirect allowlist, тестовых пользователей/claims и возможная ротация credential — требуют отдельного полномочия владельца IdP. Очистка/отзыв тестовой регистрации и пользователя также выполняется владельцем после проверки.

Этот вариант способен доказать реальный OIDC login через настоящий provider и выбранный test account, а при исполнении полного G15 runtime-сценария — browser flow через реальный ingress и owners. Он не доказывает production identity/capacity, если использовался тестовый tenant/account; не закрывает G14 или G16. Сейчас он заблокирован отсутствием issuer/client input locator и provider registration authority. Он не является необходимым доказательством только для G15 UX/integration criteria, но потребуется для отдельного production-login acceptance из `29_NGINX_TRANSPORT_AND_AUTH.md`.

## Вариант B — изолированный verification-only PKCE/JWKS профиль

Если цель — закрыть G15 browser integration без заявления о production login, ограниченный путь — кандидат с заранее закоммиченным конфигурационным вариантом, который использует только существующую синтетическую PKCE/JWKS fixture. Это отдельное изменение authority: одобрение G18 config-lineage или ранее данных runtime-разрешений на него не распространяется.

Кандидат должен быть чистым изолированным checkout с точной ancestry/base SHA и новой context/config digest. Единственное разрешённое tracked config изменение — `browserOidc` в `config/platform.yaml` из `null` в полный объект по уже существующей схеме; значения issuer/client/endpoints/claims — только из проверенной fixture. `redirectUri` выводится из уже установленного `platform.publicBaseUrl`; сам base URL, nginx profile/routes, permissions, toolchain pins и secrets schema не меняются. Запуск с runtime overlay, подменой config после admission или `page.route` не считается этим вариантом.

Для этого варианта отдельно требуется approval на синтетический ephemeral CA и IdP private-key material только через trusted `config-bootstrap` и scoped tmpfs runtime materialization; обычные временные файлы текущей fixture для этого не подходят. Private keys не должны попадать в обычный filesystem, test-runner environment, argv, логи или постоянный SOPS bundle. CA certificate передаётся read-only Edge через существующий узкий механизм `NODE_EXTRA_CA_CERTS` и импортируется только в disposable Chromium profile; в браузер не передаются private keys, а host trust store не меняется. Сертификаты и ключи существуют лишь в disposable resources и уничтожаются при teardown. Это не разрешает менять постоянные SOPS secrets. Никаких общих host CA изменений, внешних DNS/IdP операций или host `/etc/hosts` правок. Browser должен обращаться к тому же fixture issuer по TLS hostname, который покрывает IdP SAN; маршрутизация hostname выполняется исключительно внутри одноразовой изолированной сети. Внешние side effects ограничены локальным запуском disposable runtimes, run-scoped DB/Kafka и fixture account/state; после receipt обязательны teardown ресурсов и проверка cleanup. Не использовать реальный provider и не выполнять Aroma mutation/reconciliation.

Для admission нужны проверяемые правила lineage: exact parent candidate SHA, ancestry, base config SHA, результат diff allowlist только на `browserOidc`, точный config blob digest и candidate SHA; receipt связывается со всеми этими значениями. Любая иная tracked config-правка или runtime overlay отвергает профиль. G15 receipt должен отмечать `verification-only`, synthetic issuer, реальный браузер, nginx TLS ingress, owner services и run DB/Kafka identity, а также очищенные ресурсы; он не должен маркировать production login/provider identity как PASS.

Текущий realtime fixture выдаёт только `orders:read:any` и `orders:reconcile:any`; этого недостаточно для G15 Customer/Draft/Quote-пути. Verification-only account должен получать синтетические claims ровно с contract permissions, необходимыми сценарию: `customer:create`, `customer:read`, `catalog:read`, `pricing:create`, `orders:create`, `orders:edit:any`, `orders:confirm:any` и `orders:read:any`. Не выдавать `orders:reconcile:any`: G15 не должен запускать Aroma reconciliation. Отдельный negative account/profile без требуемого permission должен получить отказ на соответствующей операции; permission map production не меняется.

Такой профиль может доказать Authorization Code + PKCE, state/nonce, RS256/JWKS validation, session/cookie/CSRF и browser-facing owner/realtime flows через фактическую изолированную топологию — только если тесты выполняются без page mocks для этих путей и receipt подтверждает реальные owner effects. Сценарий сохраняет весь recovery scope §16: потерянный ответ Customer/Draft/Quote, reload до `resourceRef`, Completed read-only replay без повторного эффекта, `InProgress` и lookup unavailable/not-retained; изменение/удаление Draft item, старый GET/replay после новой карточки, первичный SSE refetch, logout/session switch и deep-link reload. Receipt связывает команды с run-scoped owner state и подтверждает отсутствие повторных DB writes при replay. Профиль не доказывает доступность настоящего IdP, production login, поведение реального пользователя, G14 telemetry, G16 provider safety или полную готовность стенда. Нынешние realtime fixture tests и `--web-served-proof` сами по себе этих доказательств не дают.

## Ограниченный результат после решения владельца

Для варианта B ограничить implementation следующими deliverables: (1) точная committed-config-only variant и ancestry/digest admission; (2) узкая fixture DNS/TLS wiring в disposable topology без host mutations; (3) Playwright-сценарий без page.route на auth/API/SSE, проходящий через nginx, Edge, реальные owner services и run-scoped stores; (4) G15 context-bound receipt с доказательствами session, deep-link/assets/API fallback, conflict/reload/realtime и teardown; (5) targeted tests на неверный digest/неразрешённый diff, SAN/issuer mismatch, auth fail-closed и неполный cleanup. Не менять schema, dependencies, pins, production auth defaults, provider behavior или остальные gates.

Вариант A вместо fixture admission использует утверждённые реальные provider inputs и отдельный provider test account; его deliverable включает доказательство provider registration/redirect/claims, но не разрешает любые provider mutations за пределами этой регистрации. В обоих вариантах `browserOidc: null` остаётся production reference default, пока owner отдельно не утвердит постоянную конфигурацию и соответствующие secrets.

## Решение, которое требуется

Нужно выбрать один scope: реальная IdP-регистрация с конкретными issuer/client inputs либо verification-only профиль на существующей локальной PKCE/JWKS fixture с committed-config lineage. Второй вариант требует отдельного одобрения именно config-only candidate variant, изолированной TLS/DNS fixture wiring и ограниченного G15 receipt; он не вытекает из предыдущего G18 approval. Пока выбор и необходимые inputs не подтверждены, не менять `browserOidc: null`, не запускать внешние IdP-операции и считать G15 интегрированный ingress/owner proof NOT_RUN.
