## Подготовленный сценарий, пока НЕ выполнен

Только действующий аккаунт на `https://aromateacoffee.ru`. Никакого checkout,
создания заказа/счёта, оплаты, изменения профиля или массовой корзины.
Используется ровно один offer, найденный повторно по `C-200-26` в свежем каталоге;
raw IDs не берутся из обезличенных captures. При непустой начальной корзине — стоп.

1. Зафиксировать свежий полный cart GET и уникальный candidate. При остановленном
   товаре, изменившейся упаковке/помоле либо неоднозначной identity — стоп.
2. Однократно POST `/api/v1/cart/`: form-urlencoded `offer_id=<fresh ID>`,
   `quantity=1`, `packing=Aroma`; `grind_id` отсутствует для зернового кандидата.
   `Aroma` здесь проверяемая гипотеза исторического sample, не принятый контракт.
3. Полностью прочитать response и отдельный свежий GET. Выяснить созданные
   cart-line IDs, quantity, packing, цены/скидки, вес и связь с offer.
4. Для единственной однозначно сопоставленной созданной строки однократно PUT
   `/api/v1/cart/{id}`: JSON `quantity=2`, `packing=Aroma`; затем полный GET.
5. Повторить тот же PUT `quantity=2` как отдельный запланированный тест
   абсолютного set, затем GET. Это не retry после ошибки.
6. Повторить POST `quantity=1` для того же offer как отдельный тест duplicate-line
   policy, затем GET. Максимум намеренно запрошено три единицы API; единицы
   измерения пока не объявляются упаковками или килограммами.
7. Удалить только строки, доказанно созданные этим тестом: один DELETE на каждую,
   не более двух строк, с GET после каждого. При вмешательстве другого клиента,
   неизвестной строке или неоднозначности не выполнять массовую очистку.
8. Один DELETE уже удалённого test-owned ID для missing-line semantics, затем
   окончательный GET. HTTP 404 сам по себе не считать подтверждением no-op.

Предел: максимум семь mutation requests, один login, не более двенадцати GET.
При timeout/обрыве после dispatch запрещён resend: сначала fresh GET, а при
неопределённом результате — остановка и отчёт о возможном остатке. Cleanup не
выдаётся за успешный, пока финальный полный GET не подтвердит исходное состояние.
Сохраняются обезличенные полные формы cart responses, request shapes без cookie
values и credentials, порядок запросов и наблюдаемые изменения.

## Предел доказательства

Даже успешный сценарий подтвердит только конкретный offer/packing и quantities
1/2/наблюдение после повторного add. Он не докажет глобальные max/min/step,
дробные количества, все варианты помола/упаковки и денежную единицу `price`.
Эти сведения нельзя распространить на весь каталог без дополнительных источников.

- Какие cookies обязательны, как истекает/обновляется сессия и как отличить
  истечение auth от запрета доступа?
