# Нагрузка CPU локальной машины — 5 ноября 2026

Значительная часть текущей нагрузки вызвана дорогими и частыми healthcheck.
Оснований приписывать всю нагрузку ошибкам бизнес-логики не получено.
При исходной диагностике runtime, конфигурация, контейнеры и данные не менялись.
Затем по отдельному поручению пользователя healthcheck изменён и применён:
средняя занятость CPU **40,41% → 21,17%** в двух трёхминутных замерах.
Методика, применение и ограничения сравнения приведены в конце отчёта.

## Причина

В `compose.yaml:77` Kafka-healthcheck запускает
`kafka-broker-api-versions.sh` с новым JVM каждые 5 секунд после окончания
предыдущего запуска. Пять штатных проверок из Docker health log занимали
около 3,5–3,94 с каждая. Дополнительный одиночный read-only запуск того же
командного пути через Bash `time` завершился успешно:

```text
healthcheck wall=4.341 user=6.258 sys=0.809
```

Итого **7,067 CPU-секунды** на одну проверку. CPU-время может превышать
реальное время из-за нескольких потоков JVM. Основной Kafka broker при этом
занимал только 7–8% одного CPU.

Общий Node-healthcheck в `compose.yaml:25` также имеет interval 5s,
применяется к 14 сервисам и каждый раз создаёт отдельный Node-процесс.
`packages/platform-runtime/src/healthcheck.ts` импортирует security/YAML,
читает scoped materialization, разбирает YAML и делает HTTPS/mTLS запрос.
Ни содержимое ключей, ни credential-файлы при анализе не выводились.

Контрольный успешный вызов `runRuntimeHealthcheck` в catalog-service:
CPU user 301635 мкс + system 98896 мкс = **0,401 CPU-секунды**, wall после
начала JS 314 мс, RSS 82 МиБ. Это стоимость всего проверочного процесса;
доли загрузки модулей, YAML и TLS отдельно не профилировались.

По `pidstat` дополнительную нагрузку создавали процессы ChatGPT/Codex,
Xorg, Chrome и x11vnc. Например, два процесса ChatGPT вместе занимали
27,21% одного CPU в первом 30-секундном интервале. Это отдельная нагрузка
настольных приложений.

У preparation есть регулярный recovery/recompute и relay с паузой 1000 мс:
`apps/orders-aroma-preparation/src/runtime-composition.ts:131` и
`src/infrastructure/preparation-store.ts:655`. Его постоянный процесс
потреблял 11,71% одного CPU, то есть около 1,46% хоста. Это возможное
направление последующей оптимизации; бесконечный цикл без ожидания здесь
не обнаружен, а необходимость recovery нельзя отменять по одному замеру CPU.

## Минимальное направление исправления

Сначала увеличить интервал тяжёлых проверок в установившемся режиме,
например до 30 с, отдельно сохранив частые проверки при запуске через
`start_interval`. Сохранить проверку Kafka API и mTLS, не заменять readiness
тестом наличия PID. Учесть увеличившееся время обнаружения отказа и проверить
startup, unhealthy и восстановление до применения к работающему стеку.
Затем повторить такой же замер. Предположение об экономии ещё не проверено
изменением настроек или A/B на работающих сервисах.

Семантика interval/start_interval сверена с
[официальной документацией Docker](https://docs.docker.com/reference/dockerfile/#healthcheck).

## Исправление и сравнение до/после

5 ноября 2026 по явному поручению пользователя изменены общий Node-healthcheck
и Kafka-healthcheck в `compose.yaml`: `interval: 30s`, `start_interval: 5s`.
Команды проверок, timeout, start_period и retries сохранены. В существующие
проверки `tests/compose/topology.test.mjs` добавлены assertions обоих интервалов
для всех 14 Node runtime и Kafka. Другие существующие изменения рабочего дерева
не входили в это исправление.

Применение выполнено штатным Docker Compose к установленным image IDs:
сначала Kafka, затем 14 Node-сервисов, с `--no-build --no-deps --pull never
--wait --wait-timeout 180`. Каждая фаза завершилась кодом 0, все 15 контейнеров
стали healthy. Новые образы, миграции и provider-команды не запускались.
Использованы прежние frozen controller и steady release override; immutable
исходники и manifest установленного release не редактировались.

Дополнение для текущего установленного release сохранено в
`/home/yurgusev/coffee-platform/runtime/overrides/healthcheck-30s.json` и включено
в Compose config_files labels новых контейнеров. Оно содержит только два

Compose отличается от прежнего только ими; image IDs, environment и mount
источники сверены с фактическими контейнерами. Команды и необходимый
`COFFEE_COMPOSE_SECRETS_DIR` записаны в приватных apply-plan/receipt.
При ручном пересоздании этого frozen release нужно сохранять последний override;
в текущем исходном `compose.yaml` оба новых значения уже заданы непосредственно.

Изменился адрес realtime-gateway. Выполнен плавный reload конфигурации nginx
через `docker exec coffee-platform-edge-nginx-1 /usr/sbin/nginx -s reload`.
