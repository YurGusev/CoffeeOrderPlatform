## Подтверждённые причины в runtime и конфигурации

### Kafka: минимальный heap 1 ГиБ

Фактические JVM flags брокера — **`-Xms1G -Xmx1G`**. В установленном образе
`/opt/kafka/bin/kafka-server-start.sh` задаёт их, когда `KAFKA_HEAP_OPTS`
не установлен. Heap изначально не может быть меньше 1 ГиБ; после работы
большая часть этого объёма уже представлена в RSS. Это явная причина базового
расхода, а не доказательство удержания 1 ГиБ бизнес-данных кодом приложения.
Применимый к текущей нагрузке меньший heap ещё не проверялся. JDK diagnostic
tools jstat/jcmd в контейнере отсутствуют; фактический live set Java heap
отдельно не измерен.

Keycloak запущен с `-Xms64m -Xmx512m`, MaxMetaspaceSize 256m, cgroup limit
2 ГиБ. Его примерно 479 МиБ также имеют понятный JVM budget; это не общий
JavaScript heap Node-сервисов.

### Два Node-процесса вместо одного в каждом сервисе

`Dockerfile` запускает `scripts/permission-enforce.mjs`. Тот вызывает
`runPermissionMode` из `scripts/permission-audit.mjs`, где после чтения config
и построения permission flags выполняется `spawn(process.execPath, ...)`.
Родитель остаётся жить, пересылает SIGTERM/SIGINT и ждёт exit дочернего процесса.

Во всех **14** Node-сервисах подтверждены два процесса Node: permission launcher
и основной `dist/main.js`. Сумма PSS launcher-процессов — **241,14 МиБ**,
Private_Dirty — 216,68 МиБ. Например, в preparation launcher занимает около
17,14 МиБ PSS, основной процесс — около 115,92 МиБ PSS. В api-public —
17,10 и 52,84 МиБ соответственно.

Это конкретный постоянный расход общего startup-кода. Устранение отдельного
родительского процесса требует сохранить permission enforcement, передачу
сигналов и exit semantics; отключение защиты ради экономии не предлагалось
и не выполнялось.

### Heap, native runtime и отдельные сервисы

У 14 основных Node-процессов суммарно около **509 МиБ heapUsed** и
673 МиБ heapTotal. Остальной working set включает permission launchers,
native библиотеки/клиенты, стеки и другие runtime allocations. RSS каждого
процесса дополнительно включает shared executable/library pages, поэтому
простое суммирование RSS завышает физическую память.

На момент исследования 13 из 14 Node-контейнеров и Kafka не имеют явного
cgroup RAM limit; realtime ограничен 512 МиБ. Значение порядка 13,64 ГиБ
после `/` в Docker stats у остальных означает доступный потолок хоста,
а не заранее выделенную память. Семантика лимитов описана в
[Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/).
Это риск для будущих пиков, но само отсутствие
лимита не объясняет текущий умеренный heap.

Очереди и кеши в затронутом коде ограничены: OTel producer — 256 spans
с ограничением сериализованной записи, Kafka — bounded queues, realtime —
ring 16 МиБ и суммарная очередь 64 МиБ. Эти бюджеты не означают их текущую
заполненность. У realtime фактически 0 соединений, 0 байт очереди,
52 записи / 13 624 байта ring. Большой SSE backlog текущую RAM не объясняет.
У всех 14 сервисов счётчики telemetry export failures, drops и overflows
на момент probe равны нулю.

## Проверка роста heap

Без inspector, heap snapshots, изменения флагов или перезапуска процессов:
read-only GET `/metrics` существующим healthcheck mTLS-клиентом. Scoped keys
обрабатывались только штатным helper внутри контейнера; выводились лишь
allowlisted числовые метрики. Пять точек с интервалом 30 с, 14:30:53–14:32:53.

| Основной процесс         | heapUsed, МиБ min–max | RSS, МиБ min–max | GC count: начало → конец |
| ------------------------ | --------------------: | ---------------: | -----------------------: |
| orders-aroma-preparation |           44,53–55,23 |    184,57–186,12 |                578 → 600 |
| aroma-convergence        |           36,59–58,29 |    188,62–189,54 |                394 → 405 |
| realtime-gateway         |           33,06–36,99 |    132,18–132,70 |              1190 → 1236 |
| api-public               |           35,16–35,55 |    116,61–117,30 |              1184 → 1234 |

Heap уменьшается между точками, RSS почти стабилен. Например, convergence
heapUsed 55,90 → 36,59 → 47,32 → 58,29 → 43,93 МиБ. Это не картина быстрой
монотонной утечки. Двух минут недостаточно, чтобы исключить медленную утечку
или рост под другой нагрузкой. RSS не равен heapUsed; Node отдельно описывает
[native memory и возможную malloc fragmentation](https://nodejs.org/api/process.html#processmemoryusage).
Fragmentation в этой задаче не установлена как причина и не выдаётся за диагноз.

## Что имеет смысл проверять следующим

1. Меньший Kafka heap на отдельном нагрузочном сценарии: возможна экономия
   сотен МиБ, но увеличение частоты GC может вернуть CPU-нагрузку.
2. Возможность убрать постоянный permission parent с сохранением всех
   enforcement/lifecycle гарантий: измеренный текущий overhead около 241 МиБ.
3. Подбор memory budgets для Node после теста рабочих пиков. Установка жёсткого
   лимита по idle RSS без проверки пиков может привести к OOM.

Настройки heap/лимитов, launcher и предыдущие CPU-оптимизации в рамках этого
исследования не применялись. Heap dumps и длительный нагрузочный тест не снимались.
Идентификаторы и StartedAt всех 27 работающих контейнеров сохранились.
