## 1. Граница аудита и шкала доказательности

Это аудит кода и нормативных материалов на `HEAD 4b2cad1dab30af66ad0b2fe64da280222e506574` с грязным, но не исправляемым snapshot-документом. Поэтому ниже строго разделены четыре уровня:

1. **Нормативная спецификация** — launch-документы и role map описывают, что должно быть создано.
2. **Фактический исходник** — SQL migration-файлы и TypeScript repository/runtime-код действительно находятся в репозитории.
3. **Намерение тестирования** — в спецификациях перечислены обязательные тесты, но наличие такого теста не равно его выполнению.
4. **Доказательство runtime** — в данном аудите отсутствует: нет live DB introspection и не найдено доказанного вызова `applyMigrations` из service composition roots.

Главный результат: пять owner DB нормативно определены, но в текущем дереве SQL-миграции материализуют только Customer и Integration. Для Catalog, Pricing и Orders есть role map/specification, но отсутствуют локальные каталоги миграций сервисов и business repositories. Это не означает, что target-БД никогда не создавались вне репозитория; означает только, что это не доказано текущим snapshot исходников.

Техническая таблица `platform_schema_migrations`, которую создаёт общий migration runner при вызове `applyMigrations`, не считается service-local migration table и не входит в число 13 фактических business/operational tables. Вызов runner-а и deployed ledger в этом аудите не доказаны.

## 2. Пять owner DB: логическое владение и физическая компоновка

**Логическое владение** означает право bounded context определять модель, инварианты, writer, owner-local transaction и миграции. **Физическая БД/схема** — изоляционная граница PostgreSQL: отдельная database и owner schema, отдельные роли migrator/runtime, отдельный connection pool. Эти понятия связаны, но не взаимозаменяемы: один bounded context может иметь несколько runtime writers с узкими grants, а события/owner API могут распространять факты без выдачи межвладельческого SQL.

## 3. Кто пишет факты и где проходит transaction boundary

Customer aggregate создаётся одним owner transaction: acquire idempotency, insert Customer, optional Address, append-only audit и completion idempotency. Source делает это через opaque `Transaction`; SQL заранее определяется owner adapter и не выдаётся application handler-у. Customer repository не читает Catalog/Pricing/Orders DB. `getOrderInput` выдаёт только customer ref/version/display name/status для Orders owner API.

Integration Gateway владеет только техническими provider facts: зашифрованной session envelope, mutation journal и provider catalog identity/export state. Gateway не хранит plaintext cookies, provider credentials, полный provider body или Orders state. Mutation `Reserved → Dispatched → terminal/UnknownOutcome` разбита короткими транзакциями вокруг unsafe HTTP; DB lock во время сетевого вызова не удерживается. Catalog export и binding writes также выполняются в Gateway-owned database и проверяются reread-ом при `TRANSACTION_OUTCOME_UNKNOWN`.

Orders, Catalog и Pricing в спецификации имеют отдельные owner transactions, но текущие service entrypoints — только `startConfiguredRuntime(...)`; business composition, repositories и migrations отсутствуют. Поэтому нельзя выдавать описанную Confirm/convergence transaction за реализованный runtime.

## 6. Межсервисные refs — логические, не SQL FK

SQL FK разрешены только внутри одного owner DB/schema. `customer_ref`, `product_ref`, `variant_ref`, `quote_ref`, `offer_ref`, `supplier_ref`, `snapshot_ref`, `order_ref`, `operation_ref` и `source_*_hash` являются typed/format-validated identifiers, но cross-owner связи проверяются owner API, event payload, snapshot compatibility и state guards.

Ключевые logical refs:

| Откуда | Куда | Канал | Что фиксируется локально |
|---|---|---|---|
| Orders → Customer | `GET /api/internal-v1/customers/{customerRef}/order-input` | synchronous owner API | customer ref/version/display name snapshot в Draft |
| Orders → Pricing | `POST .../pricing/quotes:verify` | synchronous owner API | quote hash/line, offer, money, policy/catalog/mapping revisions в item |
| Catalog activation → Orders preparation | `CatalogMappingChanged.v2` | Kafka at-least-once + Inbox | product/variant → offer/mapping/availability projection |
| Orders → preparation | `OrderConfirmed.v1` | Kafka | immutable contribution read from Orders owner projection |
| Orders preparation → convergence | `AromaConvergenceRequested.v1` | Kafka command | cart scope + Desired revision/hash |
| convergence ↔ Gateway | typed internal HTTP | reserve/journal operationRef | Gateway journal, no Orders DB access |
| observer/convergence → Orders projection | `AromaObservationChanged.v1`, `AromaConvergenceChanged.v1` | Kafka | current Observed/Attempt facts and per-Order Card projection |

Дубликаты и replay обрабатываются Inbox/idempotency/state guards; Kafka не является source of truth. Business state + Outbox должны быть одной local transaction, offset подтверждается только после durable COMMIT. Invalid wire records идут в owner-local quarantine или topic DLQ согласно mode.

## 7. Идемпотентность, Inbox, Outbox, lease/fencing и хранение

### Idempotency

Общий SQL contract требует owner-local `(actor_ref, scope, idempotency_key)` и canonical request hash. Completed response хранится durable; exact same key/hash — replay, другой hash — conflict, active lease — in progress. Acquire не должен удалять Completed или незавершённый unknown intent; cleanup принадлежит owner policy. Customer реализует это фактически с 30 s lease/24 h retention. Pricing и Orders имеют собственные planned tables и не должны переиспользовать Customer DB.

### Inbox/Outbox

В текущем source package есть generic `SqlInboxStore`/`SqlOutboxStore`, но их DDL — contract в `06_EVENTS_AND_RECOVERY.md`, а не migration, и вызов consumer wiring с actual owner tables не найден. `inbox_messages` использует message identity/payload hash/lease/attempt/state; `inbox_quarantine` — `(topic, partition, offset)` PK. `outbox_messages` использует stable message ID, continuous aggregate sequence, payload hash, state, lease token и predecessor barrier. Поэтому package API нельзя считать созданной таблицей.

### Lease и fencing

Orders convergence design использует `convergence_leases` на cart scope: owner UUID, `fence_epoch`, heartbeat 10 s, expiry 30 s; epoch монотонно увеличивается. Перед reservation, unsafe HTTP и terminal persistence повторяется conditional check owner/epoch/expiry/current Desired. Stale fence даёт ноль rows и запрещает сохранять success. Gateway journal имеет собственный reservation owner/lease, но не заменяет Orders fence и не является разрешением blind retry.

### Хранение и удаление

- Customer idempotency: 24 ч по фактическому runtime code.
- Outbox: published 168 h, failed/quarantine 720 h из `platform.yaml`.
- Kafka: topic-specific; orders lifecycle/catalog 2160 h, convergence command 168 h, cart events 720 h, realtime invalidation 1 h.
- Gateway terminal mutation journal: policy документа — не менее 90 дней после terminal completion. Реальные partial index и cleanup включают `Acknowledged`, `Rejected` и `UnknownOutcome`; истечение `retention_until` делает запись кандидатом удаления. Источники: `docs/launch/22_AROMA_GATEWAY_OPERATION_JOURNAL.md:67-84`, `apps/aroma-gateway/migrations/0006_provider_mutation_retention.sql:4-16`, `apps/aroma-gateway/src/infrastructure/database/provider-mutation-journal.ts:469-489`. В проверенных источниках нет явного правила «UnknownOutcome хранить вечно», поэтому такое правило не объявляется ни гарантией, ни установленным нарушением. Согласованность конечного retention с фактическим Orders recovery horizon требует отдельной runtime-проверки.
- Orders recovery horizon должен сохранять `operationRef` минимум 90 дней.

## 8. Money, time и version semantics

Money не должен храниться как floating point. Catalog/Gateway normalizer переводит provider decimal price в exact minor units; Catalog policy фиксирует `RUB`, Orders item хранит `unit_minor` и `line_total_minor`, а wire decimal/version значения идут canonical decimal strings. `quantity_milli` — целое положительное `bigint` для Desired/Mutation domains; provider Gateway mutation в действующем SQL допускает positive bigint и `NULL` для RemoveLine.

Времена — `timestamptz`; новые domain timestamps по authority должны идти через Temporal, а SQL defaults используют `clock_timestamp()`/`CURRENT_TIMESTAMP`. Wire `occurredAt` и owner timestamps canonicalize-ятся; PostgreSQL microsecond rounding не должен переписывать более точное исходное wire time. Lease/expiry сравниваются с PostgreSQL transaction time, а не с browser clock.

Version domains различны: Customer `version`, Orders `Order.version`, Catalog snapshot/mapping revisions, Desired/Observed revisions, convergence fence epoch, Outbox aggregate sequence и projectionVersion. Нельзя трактовать равенство Desired/Observed revision как доказательство InSync без hash, complete snapshot, current fence и terminal attempt proof.

## 9. Migration execution, recovery и schema isolation

`platform-migrations.applyMigrations` валидирует ID `NNNN_name`, порядок, SHA-256 checksum SQL и ledger prefix; под owner-local advisory transaction lock атомарно создаёт ledger, выполняет DDL и вставляет checksum row. Drift, missing checksum, orphan и non-prefix останавливают запуск. `defineMigration` запрещает embedded `BEGIN/COMMIT/ROLLBACK`; мигратор использует отдельные owner credentials. Ledger по default — `<owner_schema>.platform_schema_migrations` только если runner вызван с schema, но фактический call site и deployed ledger не доказаны.

`@coffee-platform/database/owner` допускает только owner-defined SELECT/INSERT/UPDATE/DELETE и отдельную migration DDL capability; application handlers не должны импортировать raw `pg`. Один pool runtime передаётся в composition, второй repository pool запрещён. Transaction outcome unknown уничтожает broken connection и не даёт права на automatic retry; recovery выполняется bounded reread по stable identity или через durable state.

Schema isolation — не только convention. `database-role-map.json` ограничивает grants по таблицам и runtime; runtime roles не получают DDL/CREATEDB/CREATEROLE и не получают чужую DB. Однако role map и SQL-файлы — статические источники, не доказательство, что grants реально применены. Для durable malformed-record admission остаётся явная gap: `inbox_quarantine` описана в delivery contract, но не перечислена в role map и не создана migration-ом.

## 10. Fleet pool budgets: установленное расхождение

Точный текущий `config/platform.yaml` задаёт PostgreSQL `maxConnections: 96`, `reservedConnections: 32`, `rolloutReplicas: 1`. DB-backed runtime pools: Customer 8; Catalog 8 + supplier sync 4 + activation 4; Pricing 8; Orders service 4 + preparation 4 + observer 4 + convergence 4; Integration Gateway 8. Сумма steady = **56**, largest pool = **8**, serial rollout = **8**, reserve = **32**, required = **96**. Это соответствует admission code: он суммирует `replicas * dbPool.max`, берёт largest pool для rollout и отвергает budget, если required > max.

Есть нормативное расхождение, его нельзя смешивать:

| Источник | Orders pool | Steady total | Reserve/rollout | Интерпретация |
|---|---:|---:|---:|---|
| `docs/launch/11_CONFIGURATION_AND_SECRETS.md` | 12 | 64 | 32 reserve; `max_connections>=96` | более старая/неактуальная цифра в snapshot-документе |
| `config/platform.yaml` | 4 | фактически 56 | 32 reserve + 8 serial rollout | текущий executable config |
| `docs/launch/23_RUNTIME_CONFIGURATION_MATRIX.md` | 4 | 56 | 32 + 8 = 96 | актуальная matrix authority |
| `packages/platform-config/src/index.ts` | вычисляется из input | вычисляется | `largestPool * rolloutReplicas` | actual admission algorithm |

Поэтому эта запись фиксирует `12/64` только как устаревшее расхождение документации. Для runtime admission и fleet capacity следует использовать `4/56/8/32/96`, не исправляя репозиторий в рамках аудита.

## 11. Итог аудита

- Нормативно определено **5 owner DB / 5 owner schemas**.
- В source snapshot найдено **9 SQL migration files**: Customer 2, Integration 7.
- Эти SQL описывают **13 конкретных business/operational tables**: Customer 5 и Integration 8. Они не являются доказательством deployed state.
- Catalog, Pricing и Orders имеют проектные таблицы и grants, но не имеют materialized service-local migrations в текущем репозитории.
- Generic Inbox/Outbox/Idempotency packages — executable code/contracts, но не deployed schema. Фактическая Customer idempotency и Integration mutation journal — разные bounded-context механизмы.
- Physical FK имеются только внутри Customer и Integration catalog-export subtree. Межсервисные refs — API/event/projection invariants, не SQL FK.
- Migration runner и pool admission реализованы как foundation source; runtime migration execution/live grants не доказаны.
- `inbox_quarantine` требует отдельной owner migration/grant перед durable malformed-record admission.
- Pool discrepancy зафиксирована как `11_CONFIGURATION_AND_SECRETS.md:233-241` = 12/64 против текущих config/matrix/code = 4/56 and 96 required.
