## 1. Что нельзя считать уже работающей системой

**Топология и foundation не равны завершённому бизнес-пути.** В `apps/*/src/main.ts` существенная композиция найдена у Customer, Gateway и частично API roots. Остальные entrypoints в основном вызывают общий bootstrap. Общие transaction/Inbox/Outbox/Kafka helpers есть, но сами по себе не создают owner migrations, event bindings, Catalog activation, Pricing, Orders lifecycle или convergence. Детальный каталог — [01_Границы и runtime](01_%D0%93%D1%80%D0%B0%D0%BD%D0%B8%D1%86%D1%8B%20%D0%B8%20runtime.md), [04_Схема PostgreSQL](04_%D0%A1%D1%85%D0%B5%D0%BC%D0%B0%20PostgreSQL.md), [05_HTTP и события](05_HTTP%20%D0%B8%20%D1%81%D0%BE%D0%B1%D1%8B%D1%82%D0%B8%D1%8F.md). Источники: `docs/launch/13_DELIVERY_DEPENDENCY_GRAPH.md:53-101`; `apps/orders-service/src/main.ts:1-3`; `apps/aroma-convergence/src/main.ts:1-3`.

**AROMA Gateway не заменяет Orders convergence.** Реализованный technical journal защищает provider-call identity и исход, но не агрегирует подтверждённые заказы в cart Desired и не вычисляет per-order `InSync`. Обязательны current Desired, complete Current Observed, fence и terminal proof. Источники: `docs/launch/19_AROMA_CONVERGENCE_IMPLEMENTATION_SPEC.md:208-252`; `docs/launch/22_AROMA_GATEWAY_OPERATION_JOURNAL.md:1-5`.

**Frontend и realtime пока не принимаются по макетам.** `apps/web/src/main.ts` — Node bootstrap; runtime package, OpenAPI, generated types, UX/SVG/HTML и ADR не являются browser shell, QueryClient, EventSource, accessibility или SSE fanout. Смотри [06_Frontend и каналы](06_Frontend%20%D0%B8%20%D0%BA%D0%B0%D0%BD%D0%B0%D0%BB%D1%8B.md).

## 2. Подтверждённые расхождения документов и materialization

Под «расхождениями» ниже понимается также разница между общей wire-формой, более узким исполнимым ограничением и ещё не реализованной спецификацией — не каждое наблюдение является дефектом.

Количество Gateway дополнительно ограничено явным решением владельца: целые упаковки/штуки `1..Number.MAX_SAFE_INTEGER` (`docs/launch/22_AROMA_GATEWAY_OPERATION_JOURNAL.md:105-114`). Общий schema `ProviderQuantity` допускает decimal string с дробью (`contracts/schemas/common/money-version-time.v1.schema.json:19-22`), но это не отменяет исполнимое ограничение. Нельзя автоматически назвать отказ на дроби багом или молча округлять её.

Retention также нельзя выводить из желаемого поведения: фактический Gateway cleanup включает `UnknownOutcome` после `retention_until` (`apps/aroma-gateway/src/infrastructure/database/provider-mutation-journal.ts:477-489`). Документ задаёт 90-дневный terminal horizon, но явного правила вечного хранения unknown в прочитанных источниках не найдено. Поэтому атлас описывает факт и непроверенную согласованность с Orders recovery horizon, а не выдумывает нарушение.

Репозиторий в рамках подготовки атласа не исправлялся. При следующей реализации сначала уточнять соответствующую authority и узкий acceptance criterion, а не «лечить» расхождения переписыванием immutable roots.

## 3. Разные уровни AROMA-модели, которые нельзя слить

Канонический root хранит развитые `EffectiveDesired`, `AromaSemanticLineKey`, per-line state и `ResolvedAsSucceeded|ResolvedAsFailed` recovery outcomes. Прикладной first-launch документ определяет scope `aroma-primary`, frozen `offerRef`, aggregate cart Desired и конкретные SQL имена; автоматически remap подтверждённого Order на новый offer запрещён.

`Confirmed Order` → immutable contribution → preparation transaction → cart Desired — не одна синхронная provider-команда. Одна cart Attempt допускает максимум одну reservation/mutation. Gateway Acknowledged означает технический ответ; `InSync` устанавливается только Orders-owned proof. После `UnknownOutcome` не повторяется старый unsafe dispatch: recovery начинается с fresh complete GET.

В атласе эти уровни разведены в [08_AROMA сходимость](08_AROMA%20%D1%81%D1%85%D0%BE%D0%B4%D0%B8%D0%BC%D0%BE%D1%81%D1%82%D1%8C.md). Источники: `docs/launch/19_AROMA_CONVERGENCE_IMPLEMENTATION_SPEC.md:6-16,79-123,208-252`; `docs/launch/22_AROMA_GATEWAY_OPERATION_JOURNAL.md:67-84` и canonical M11 sources соответствующей главы.

## 4. Неустановленные provider semantics

- Наблюдения за отдельными SKU/ответами не устанавливают общий provider contract для currency, unit/packing, quantity step, всех grind options и promotions.
- Manual redirects / bounded local session cache не доказывают provider TTL или наличие refresh protocol.
- В проверенном Gateway не найден явно выделенный rate limiter/circuit breaker, обещанный более общей архитектурой. Это ограниченное source-level отрицательное наблюдение, не результат нагрузочной проверки.
- Latest source identity proof защищает binding consistency, но не делает всякий provider body бизнес-истиной Catalog или Pricing.
- Историческое evidence #10 не становится новым live PASS на текущем SHA.

Ссылки и точные границы исследованного протокола: [07_AROMA протокол](07_AROMA%20%D0%BF%D1%80%D0%BE%D1%82%D0%BE%D0%BA%D0%BE%D0%BB.md), `docs/launch/27_AROMA_PROVIDER_PROTOCOL.md`, `docs/launch/28_AROMA_CATALOG_PRICING_POLICY.md`. В этой работе никаких AROMA probes не выполнялось.

## 5. Launch, вторая волна и более широкий будущий scope

Launch scope — операторский Customer/Catalog/Pricing/Orders flow и безопасная AROMA cart convergence. Вторая волна добавляет Supplier Submission, Supplier Invoice/receipt/allocation/payment/checkout согласно `docs/wave-2/README.md`. Hermes/VK, полноценный Work Center и часть других контуров перечислены как не входящие в **обязательный** W2 cycle (`docs/wave-2/README.md:103-109`). Их canonical architecture сохраняется как будущее развитие; нельзя объявлять их реализованной второй волной.

PDF automation не должна подменять Invoice truth: binary belongs to ArtifactRef, invoice owner хранит interpreted facts/reconciliation, Payments — verified payment facts. Provider submit, payment и document processing требуют отдельных unknown-outcome, identity, idempotency и acceptance путей; наличие документов не закрывает эти пути.

## 6. Что нужно для следующих уровней уверенности

| Уровень | Нужное доказательство | Есть в данном атласе? |
|---|---|---|
| Source inventory | физические files, exact source refs, hash/line validation | да, см. итоговый локальный validation report |
| Schema deployed | применённый migration ledger, roles/grants, actual constraints в разрешённой target DB | нет |
| HTTP live | trusted request с реальными runtime composition и отрицательными trust cases | нет |
| Durable behavior | duplicate/crash/restart/commit-unknown/rebalance evidence | не запускалось; есть описание требований и исходников |
| Provider protocol today | отдельно разрешённые sanitized probes/controlled sandbox gates | нет |
| Browser/UX acceptance | production bundle, browser flow, accessibility, owner acceptance | нет |
| Release/deployment | exact SHA, все mandatory gates, immutable image/config digests, backup/rollback evidence | нет |

## 7. Как не потерять точность при развитии проекта

При появлении owner migration обновить **сразу** таблицу физического DDL, Mermaid FK и inventory. При появлении handler поменять только source status, не ставить deployed/accepted без исполнения. При реализации Orders или frontend перечитать API/AROMA главы: прежний план может перестать соответствовать принятому контракту. После смены revision или provider semantics старое evidence сохранить как историческое; новую дату ставить только после повторной проверки.

Не закрывать эти пробелы оптимистическими словами в Obsidian. Память должна помогать найти точное ограничение, а не создавать ложную уверенность.
