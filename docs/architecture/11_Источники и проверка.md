# Источники, проверка и обновление

[Карта атласа](README.md) · [Расхождения](12_%D0%A0%D0%B0%D1%81%D1%85%D0%BE%D0%B6%D0%B4%D0%B5%D0%BD%D0%B8%D1%8F%20%D0%B8%20%D0%BD%D0%B5%D0%B7%D0%B0%D0%B2%D0%B5%D1%80%D1%88%D1%91%D0%BD%D0%BD%D0%BE%D0%B5.md)

## 1. Происхождение и authority

Атлас составлен по первичным документам и исходникам CoffeeOrderPlatform: AGENTS, ADR, launch/wave-2/UX, применимым каноническим бизнес-инвариантам, composition roots, runtime libraries, SQL migrations, OpenAPI/JSON Schema, registry и тестам. Это производная карта, не новая authority и не импорт legacy runtime.

При публикации исходники сверены с accepted `develop` на `4b2cad1dab30af66ad0b2fe64da280222e506574`. Из 173 файлов 172 совпали с первоначальным рабочим срезом. Единственное различие — локальная дополнительная строка навигации в `docs/launch/README.md`: при переносе она исключена, hash и диапазоны приведены к accepted base. Сам документ политики каталога существует в base; его содержание не менялось. Исходный vault не переписан.

Исторические evidence/handoffs не выдаются за повторно выполненные проверки. Ни deployed topology, ни фактические SQL grants, ни provider account, ни product acceptance этим атласом не подтверждаются. Дата `verified` относится к чтению источников; `status: reference` не означает production PASS. Версии здесь — pins проекта, не утверждение о последних upstream releases.

## 2. Приложения

- [source-manifest.json](source-manifest.json): source commit, относительные пути, SHA-256, line counts и пояснение обновления единственного source file.
- [schema-inventory.json](schema-inventory.json): владельцы, схемы, фактический DDL, ключи/ограничения и отдельно спроектированные таблицы. Общий migration ledger не входит в 13 service-local DDL tables.
- [contract-inventory.json](contract-inventory.json): физические HTTP/event contracts и найденные registrations; наличие route не означает deployment reachability.
- [Актуальный exact registry](../../config/toolchain-versions.json): единственная authority pins; дублирующая исполнимая конфигурация в атлас не добавляется.
- [validation-result.json](validation-result.json): фактические результаты проверки опубликованного дерева.
- [mermaid-result.json](mermaid-result.json): исторический результат parse/SVG проверки двух схем; остальные 12 отмечены `NOT_RUN`.
- [validate_atlas.py](validate_atlas.py): адаптированный read-only validator, Python standard library, без установки dependencies и подключений к сервисам.

Личные заметки, настройки рабочего места, локальные snapshots, секреты, provider bodies, PII и полные логи не публикуются. Хеши используются для происхождения несекретных источников, не как замена encryption. Secret-файлы не входят в manifest.

## 3. Ссылки и source spans

Внутренние главы связаны обычными относительными Markdown-ссылками. Ссылки на исходники ведут к файлам того же репозитория; для диапазонов используется fragment `#L…`. Поддержка перехода к строке зависит от viewer. Для исторического воспроизведения использовать `source_commit` из manifest, а не автоматически считать текущую ветку тем же срезом.

В тексте формат `путь-к-файлу:120-145` означает файл и диапазон строк. Сокращённый `:150-160` после полного пути относится к тому же файлу. Несколько диапазонов могут перечисляться через запятую. Валидатор проверяет явно полные spans; смысл ссылок и сокращённые продолжения проверяются чтением. Совпадение hash не доказывает семантическую корректность каждого вывода.

## 4. Воспроизводимая проверка

Из корня checkout:

```sh
python3 docs/architecture/validate_atlas.py
python3 scripts/validate-launch-authority.py
python3 -m unittest discover -s tests/authority -p 'test_*.py'
git diff --check
```

Первая команда проверяет source hashes/line counts, frontmatter, относительные ссылки и line anchors, явные source spans, парность code fences, JSON, отсутствие локальных путей и неопубликованных wikilinks. Она также независимо сопоставляет inventory с `CREATE TABLE`, `REFERENCES` и `CREATE INDEX` в прикладных SQL migrations. Это узкий read-only контроль документации, не новый product test framework.

Ожидаемый состав среза: 13 глав, 173 источника, 9 SQL migrations, 13 прикладных таблиц, 10 физических FK, 14 именованных вторичных индексов. Проверка результата не обращается к PostgreSQL, Kafka или AROMA.

### Ограничения Mermaid

В атласе 14 Mermaid-блоков. В исходной локальной подготовке два блока (инфраструктура и надёжность) прошли parse и SVG generation движком Obsidian. Проверка остальных 12 не выполнилась из-за истечения запроса разрешения и не повторялась. Это `PARTIAL`, не общий PASS; новый GitHub-renderer или visual/layout acceptance не проверялся. Статический validator считает блоки, но не проверяет Mermaid grammar.

## 5. Обновление

1. Прочитать затронутые главы и проверить актуальные HEAD/status/source hashes.
2. При drift исследовать изменение authority и caller, а не просто заменить hash.
3. Согласованно обновить связанные главы: SQL ↔ business; API ↔ frontend; journal ↔ convergence; permissions ↔ topology; recovery ↔ verification.
4. Сохранить различие `spec`, `contract-only`, `scaffold`, `implemented-in-code`, historical evidence и unknown; не заполнять пробелы предположениями.
5. Обновить source manifest и inventories одной согласованной ревизией, затем выполнить приведённые проверки. Product tests выбирать по реальному изменению поведения.
6. Повторить Mermaid/visual проверку отдельно, если она разрешена и нужна; отсутствие такой проверки не маскировать.

Фоновая синхронизация не создаётся. Обновление документации само по себе не разрешает deployment, provider mutation или изменение бизнес-данных. Product acceptance имеет отдельные gates, описанные в главе о надёжности.
