# AROMA: почасовой каталог, цены и недельные акции

Статус: решение пользователя от 2026-09-14 для дальнейшей разработки.
Период обновления — **60 минут**. Документ фиксирует требуемое поведение,
а не готовность текущего runtime, wire contract или issue #10.

## 1. Основание и границы решения

- [Catalog](15_CATALOG_IMPLEMENTATION_SPEC.md) владеет полными снимками,
  вариантами, ценами, правилами акций и их активацией.
- [Pricing](16_PRICING_IMPLEMENTATION_SPEC.md) владеет вычислением цены,
  политикой и неизменяемыми quotes; Orders сохраняет согласованную цену.
- [Gateway protocol](27_AROMA_PROVIDER_PROTOCOL.md) описывает наблюдения AROMA.
- [Наблюдения 14 сентября](../../evidence/aroma-provider/2026-09-14-pricing-observations.json)
  содержат выбранные поля API и receipts запросов. Это отчёт, не полный wire
  capture и не decoder fixture. Сырые ответы и credentials в нём отсутствуют.

Неизменяемые канонические документы не редактируются. Runtime-код, модели БД
и типы CoffeeOrderSystem не переносятся. Его почасовой importer и хранение
provider discount rules использованы как evidence поведения.

## 2. Что подтверждено

Полный API-обход 14 сентября получил 464 товара на 47 страницах. Пять товаров
содержали `discount=10`, `min_weight=0`; правила созданы 14 сентября:

| Артикул | Товар | Цена API | Расчёт минус 10% |
|---|---|---:|---:|
| M-4-0075 | Воронка керамическая v02 1-4 | 549 | 494,10 |
| GT-1-0081 | Дегустационный набор чая «ЭКО Купажи» | 333 | 299,70 |
| G-5-0008 | Крем-мёд с черносливом | 158 | 142,20 |
| M-11-0038 | Типод с деревянной ручкой и крышкой 500 мл | 1211 | 1089,90 |
| G-7-0016 | Чай чёрный в пирамидках Ассам FBOP 20 шт | 150 | 135,00 |

Последняя колонка вычислена локально. Итоговое округление этих товаров
в корзине AROMA не проверено.

Для чашки M-11-0034 сохранённый ответ 12 сентября содержал цену 495 и акцию
10%; новый ответ 14 сентября — цену 446 и `discount=[]`. Пользователь
подтвердил на сайте цену **446 рублей за чашку**. Причина изменения цены API
не установлена; нельзя утверждать, что поставщик просто включил старую скидку
в новую цену.

Для кофе C-200-26 каталог вернул 620. В сохранённых cart responses 12 сентября
`products[].price` равнялось 620 при quantity=1 и 1240 при quantity=2;
`total_with_discount` — 434 и 868. Вложенное `products[].offer.price=852.6`
не совпало с этими значениями. Его назначение не установлено.

Пользователь сообщил, что акции меняются еженедельно. API передал даты
создания/обновления правил, но не явный срок окончания. Не вычислять
`expiresAt = created_at + 7 дней` и не считать `created_at` доказанным validFrom.

## 3. Три самостоятельных значения цены

1. **Цена каталога поставщика** — текущее `offers[].price` конкретного offer
   из полного проверенного снимка. Сохранить её без вычитания скидки.
2. **Расчётная цена акции** — результат применения подходящего товарного
   правила к цене каталога. Это не доказательство окончательной закупочной суммы.
3. **Фактическая закупочная цена** — отдельно подтверждённая стоимость
   конкретной строки корзины/заказа/счёта AROMA с учётом количества и скидок.
   Такой факт не переписывает глобальную цену Catalog.

Принятое monetary mapping для AROMA: `offers[].price` выражается в рублях,
`currency=RUB`, нормализация в minor units — умножение на 100. Основание —
сопоставление API и сайта для чашки, подтверждённое пользователем. Примеры:
446 → 44600, 549 → 54900. Это зафиксированное правило интеграции, а не наличие
поля currency в ответе provider.

### Policy владельца от 18 сентября 2026

Пользователь подтвердил: количество означает число упаковок/штук. Offer с весом
`0.2 кг` описывает фасовку, а `quantity=2` — две такие упаковки; `offers[].price`
является ценой одной упаковки без пересчёта на килограмм. Для товаров, которые
продаются поштучно, действует та же единица `piece`. Это owner policy текущего
контракта, а не provider unit metadata: `sold_by_piece=false` не блокирует
нормализацию `unit=piece`, если остальные обязательные факты валидны.

Вес остаётся display-фактом offer: наблюдения `200/1000` для кофе и `100/500`
для чая отображаются в килограммах/фасовке и не меняют quantity unit или цену.
Policy не выводит `packing` или `grind_id`; эти поля остаются отдельной
неразрешённой identity/mutation семантикой.

Десятичные суммы обрабатывать точно, без binary floating point. Если исходная
сумма не представима в копейках без округления, не вводить скрытое округление:
требуется отдельное подтверждённое правило. Нулевая цена сохраняется точно как
`0` minor units; normalizer переводит такой offer из `Available` в локальное
`Unavailable`, а `Stopped` сохраняет. Это локальная Platform safety policy и
не является утверждением о supplier stock или бесплатной доступности товара.

Цена относится к точному offer/варианту. В историческом provider observation
для C-200-26 единица quantity соответствовала упаковке 200 г; это наблюдение
само по себе не являлось общей provider schema. Действующая owner policy выше
задаёт количество упаковок/штук для текущего контракта и не превращает цену
упаковки в цену грамма.
`cart.products[].price` — сумма строки в проверенном сценарии; она не является
ценой единицы без учёта quantity. Не использовать вложенное cart offer.price
как fallback для цены каталога.

## 4. Правила скидок

Catalog хранит цену и нормализованные правила отдельно в одном поколении:
процент, min_weight, известную область применения и переданные provider даты.
Gateway не передаёт raw provider IDs, user IDs, cookies или body в Catalog;
нужную связь правила с продуктом выражает внутренний контракт.

- Явный `discount=[]` в полном валидном снимке удаляет прежние товарные правила.
  Полный снимок заменяет набор правил, а не только добавляет новые.
- Отсутствующий обязательный массив, invalid rule или незавершённый обход
  не считаются пустым набором скидок и не изменяют активные факты.
- Процент, условия и область применения проверяются до использования правила.
  Положительный min_weight нельзя интерпретировать как вес упаковки или всей
  корзины без подтверждения provider semantics. Для пяти наблюдённых акций он 0.
- Правила не складываются автоматически. Не копировать legacy `max(group,
  promotion)` как доказанное правило AROMA. При нескольких подходящих правилах
  или неизвестных условиях расчёт акции недоступен до определения политики;
  каталожная цена и сами факты остаются доступными.
- Расчёт `price × (100 − percent) / 100` не выдавать за сумму provider checkout.
  Если результат требует округления, его режим должен быть явно утверждён;
  не заимствовать автоматически CEILING нашей клиентской наценки.
- Отсутствие товарной акции не доказывает отсутствие персональной или объёмной
  скидки аккаунта. Такие правила не придумываются из единственного cart example.

## 5. Обновление и фиксация

Период безопасного полного чтения — **один час / 60 минут**. Schedule принадлежит
`catalog-supplier-sync`; реализовать его параметр в `config/platform.yaml`
вместе со schema и config validation в #6. Сейчас этот документ не создаёт
нового исполнимого config key. Другого источника настройки или нового scheduler
service не вводить. Не более одного текущего импорта на supplier scope;
ручное обновление проходит через тот же lease/fence и pipeline.

```text
AROMA API → Gateway → Catalog sync/staging
→ проверка полноты/identity/money/rules/binding
→ атомарная активация Catalog generation → Catalog API → Pricing
```

Товары, варианты, доступность, цены и правила акций активируются вместе.
Ошибка, partial response, timeout или конфликт оставляют прежнее поколение
активным. Время успешной проверки обновляется только после полного успешного
чтения и проверки, а не после попытки запроса. Хранить отдельно время наблюдения
и время активации; длительная обработка не делает старые данные свежими.

Повторный неизменившийся полный снимок подтверждает время проверки. Он не
создаёт новую запись истории изменения цены лишь из-за нового timestamp;
технический receipt обхода сохраняется отдельно от изменения коммерческих фактов.

Интерфейс показывает последнее успешное обновление и ошибку/задержку нового
цикла. Почасовой polling гарантирует проверку по расписанию, а не отсутствие
изменений AROMA между запросами. Полный обход страниц также не доказывает
атомарный provider snapshot. Предложенные ранее 15 минут polling и автоматическая
блокировка через 30 минут **не приняты**. Новую жёсткую freshness-блокировку
заказов этим документом не вводить.

## 6. Pricing и Orders

Gateway нормализует provider facts; Catalog хранит их версии; Pricing владеет
вычислениями и нашей политикой; Orders — согласованной ценой заказа.
Интерактивные чтения используют Catalog API, не обращаются к AROMA и не читают
чужую БД. Quote сохраняет источник Catalog и policy version.

Действующая клиентская формула #7 и TTL quote **900 секунд** не меняются.
Supplier promotion не становится автоматически клиентской скидкой. Применение
акций к коммерческому расчёту и их отображение оформить отдельным bounded
Pricing/UI delivery issue: текущий #7 прямо исключает discounts/promotions.
До этой реализации нельзя называть базовую quote «ценой с учётом всех скидок AROMA».

Ни почасовой импорт, ни исчезновение акции не переоценивают выданную quote или
подтверждённый заказ скрыто и не создают cart mutation. Новая цена применяется
через новый ценовой расчёт/явное действие; фактическая закупочная стоимость
относится к соответствующему supplier order/invoice proof.

| Владелец | Следующее действие |

| #6 Catalog import | Почасовой schedule, получение полного снимка вместе с правилами, staging и проверки. |
| #16 Catalog activation | Атомарно активировать товары/цены/правила; удалить исчезнувшие акции только при полном новом снимке; сохранить историю изменений и время проверки. |
| #17 Catalog API | Согласованно передавать Pricing факты нужной версии без provider identifiers и прямого provider HTTP. |
| Отдельный Pricing/UI scope после определения контрактов | Реализовать расчёт/показ акций с понятной областью применения, не менять молча существующую формулу #7 и не переносить legacy Orders pricing. |

Текущий `NormalizedCatalogOffer` уже содержит supplierUnitMinor, currency и
`supplierPromotions`, включая нормализованные discount rules. Их downstream
wire/storage реализация должна быть изменением контракта с downstream handoff;
одного изменения decoder недостаточно. Источники schema
меняются первыми, generated files — только генератором. Не подменять текущий
normalizer выдуманными unit, availability, image или packing/grind facts.
Независимые гарантии session/journal/mutation не переписывать ради этого решения.

## 8. Проверка реализации

Расширять существующие целевые tests; новый verification framework не нужен:

- schedule использует 60 минут, parallel/manual trigger не создаёт второй import;
- 446 RUB нормализуется в 44600 minor без float/повторной конвертации;
- цена 549 и правило 10% дают расчёт 494,10 с сохранением исходной цены;
- 495 + 10% → новый полный снимок 446 + [] удаляет прежнее правило без двойной скидки;
- partial/invalid rules response сохраняет прежнюю активную цену и набор акций;
- новая цена и правила доступны одной snapshot revision, история не переписывается;
- unknown condition/overlap/rounding не превращается в выдуманную итоговую цену;
- quote и подтверждённый Order не меняются после синхронизации;
- реальный формат cookie Expires с дефисами принимается без ослабления domain/TLS;
- evidence различает наблюдённые API поля, расчёт, пользовательское подтверждение
  и непроверенную сумму provider cart/checkout.

Наличие этого документа не закрывает acceptance #10, не меняет его галочки
и не разрешает merge, deployment или новые provider mutations.
