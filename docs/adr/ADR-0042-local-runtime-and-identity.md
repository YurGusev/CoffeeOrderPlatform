# ADR-0042: постоянный локальный запуск и identity оператора

Статус: решение владельца принято 1 ноября 2026 года; реализация и проверки ещё не завершены.

## Основание

Владелец запросил рабочую новую платформу на одном сервере и явно согласовал Keycloak 26.8.1, одну собственную учётную запись, HTTPS, отдельную служебную БД на существующем PostgreSQL и SOPS/tmpfs. После проверки готового Quay-образа согласована упаковка готовой дистрибуции Docker Hardened Images на Eclipse Temurin JRE Alpine без компиляции исходников Keycloak или Java. Существующий постоянный стек наблюдаемости не является запущенной бизнес-платформой.

Authority: [ADR-0025](ADR-0025-fastify-launch-recovery.md), [транспорт и авторизация](ADR-0031-nginx-transport-and-application-auth.md), [reference deployment](../platform/LOCAL_PLATFORM.md), [PostgreSQL bootstrap](../platform/POSTGRES_BOOTSTRAP.md), [launch verification](../launch/21_LAUNCH_VERIFICATION_SPEC.md).

## Решение

- Поставлять готовую DHI-дистрибуцию Keycloak на готовом Temurin JRE Alpine через существующий Dockerfile/G12 путь. Оба входных image digest и проверяемые fingerprints находятся только в `config/toolchain-versions.json`; итоговый image ID/OCI связывается с Source и проверенным G12 receipt. Путь Quay заменён. Компиляция исходников Keycloak/Java, Maven и `start-dev` не используются.
- DHI требует существующую авторизацию Docker Hub. Trusted bootstrap импортирует её в encrypted `bootstrap.dockerHubPullAuth`; G12 получает только отдельный Docker config в tmpfs и удаляет его при любом завершении. Общий bundle не передаётся Docker, build context или сканеру образов; права учётной записи не расширяются.
- До активации обязательны scan точного итогового образа без неразрешённых HIGH/CRITICAL и проверка обоих входных материалов. Поскольку сканер не инвентаризирует JRE из binary tar, отдельно обязательны vendor fixed-build proof и физическое связывание JRE/truststore с закреплённым Temurin; отсутствие findings не подменяет эту проверку. Результаты прототипа не считаются G12 итогового release.
- Kafka и Keycloak точечно обновляют установленный `libexpat` до `libexpatVersion` из `config/toolchain-versions.json`, для устранения CVE-2026-117610 и CVE-2026-118370. Сравнение полного APK inventory допускает только заданные изменения пакетов; закреплённые базы и проверка неизменности JRE/truststore сохраняются.
- Базы Trivy монтируются в сканер readonly. Полные SHA-256 обеих баз вычисляются после загрузки и после всех целей; вокруг каждого анализа сохраняются проверки freshness, metadata и идентичности файла через открытый descriptor и путь, включая inode, размер, режим и timestamps. Это сокращает повторное чтение баз, сохраняя контроль их неизменности, полный набор SBOM/сканов и принятый бюджет G12.
- Identity владеет отдельной служебной БД и ролью на существующем PostgreSQL. Пять владельческих бизнес-БД и их inventory остаются отдельными; legacy-БД и пользовательские volumes не изменяются.
- Единственный локальный экземпляр в development использует `localIdentity.cacheMode: local` при обычном `start`. Фактический запуск подтвердил несовместимость стандартного `jdbc-ping` с выделенным пулом 2: он требует минимум 4 соединения. Локальный кэш соответствует этому профилю и сохраняет общий DB budget; кластерная отказоустойчивость не предоставляется, identity и пользовательские сессии остаются в PostgreSQL. См. [кэширование Keycloak](https://www.keycloak.org/server/caching).
- Один пользователь получает только объединение требуемых разрешений существующего client-v1 browser inventory. Использовать существующий OIDC Authorization Code + PKCE S256 и public client, RS256, точный HTTPS callback, строковый actorRef и плоский массив permissions; новые права не добавляются.
- Issuer и его HTTPS endpoints должны реально работать из браузера на сервере и из Edge container. DNS/SAN и доверие CA проверяются на target; TLS verification не отключается. Наружу listener не публикуется.
- Все несекретные параметры читаются из immutable `config/platform.yaml` соответствующего release. Пароли, private keys и credentials находятся только в encrypted SOPS bundle; общий bundle расшифровывает trusted config-bootstrap, runtime получает собственную tmpfs материализацию.
- Измеренный первый старт Keycloak с инициализацией БД потребовал около 61 секунды до readiness. `localIdentity.startupGraceMs: 90000` задаёт отдельное окно первоначального старта; общий health timeout, interval и failure threshold не меняются.
- `--prepare-development-runtime` разрешён только для development: недостающие credentials создаются без перезаписи существующих, service certificates выпускаются действующей CA из `security.serviceTransportAuthority` на 24 часа и проверяются по точным DNS SAN. Подготовка обновления начинается за 6 часов; публичная TLS-пара и её издатель остаются отдельными. Контроллер реализует обслуживание через reload и подготавливает service/timer каждые три часа; install не включает timer. Включение timer допускается после проверки реального продления, сохранности данных и доставки/отображения предупреждений на target.
- 2 ноября 2026 владелец отдельно разрешил локальный RSA CA для публичного HTTPS интерфейса и Keycloak: NSS на target отвергает существующий Ed25519 Service CA. Однократная явная команда `--prepare-development-runtime --provision-public-authority` сохраняет issuer key только в `security.publicTransportAuthority` (SOPS), перевыпускает публичные листья с сохранением ключей и SAN; внутренний Service CA и Kafka не меняются. Повторная команда не заменяет существующий CA. Срок публичного CA — `security.publicAuthorityValidityHours: 8760`, edge leaf — `security.publicCertificateValidityHours: 2160`; identity leaf сохраняет 24 часа и существующий цикл обновления. Импорт публичного CA выполняется отдельно в хранилище пользователя после проверки fingerprint.
- Локальный PostgreSQL сохраняет server limit 100 и platform budget 96 с резервом 32. Keycloak использует pool 2; AROMA Gateway — 6, остальные Node pools не меняются. Admission учитывает 54 Node + 2 identity + 8 serial rollout + 32 reserve = 96. Initial/min/max Keycloak равны 2; фактические login/restart проверяются до приёмки.
- Постоянный Kafka использует сохранённые данные, ready verified image и постоянную scoped SASL_SSL/PKI материализацию. Однодневный synthetic fixture и placeholder image marker не считаются постоянным запуском.
- Штатный bootstrap использует существующие PostgreSQL, migrations, Compose и scoped materialization механизмы. Команда запуска проверяет точный server identity и владельцев, поднимает 14 Node roles, native nginx, Kafka и Keycloak, сохраняя существующую наблюдаемость. Повторный запуск не создаёт второе окружение и не удаляет данные.
- Normal release имеет `databaseIsolation.enabled=false` и `kafkaNamespaceIsolation=false`, без disposable launch context. Отдельно фиксируются code SHA, config SHA, image IDs, public certificate/CA identities и версии scoped materialization в существующем release bundle.
- Formal G00–G19 остаётся доказательством ровно своего кандидата. PASS другой конфигурации не переносится на normal release; его readiness/login/API/DB/Kafka/SSE и persistence проверяются на target отдельно. Runtime isolation guard и лимиты launch gates сохраняются.
- Чтение существующих Kafka PKCS12 для проверки сроков использует legacy provider OpenSSL: truststore от установленного keytool содержит RC2-40-CBC. Это только декодирование с проверкой MAC и `-nokeys`; создание хранилищ, ключи и доверенные CA не меняются.
- AROMA mutations остаются выключенными до соответствующего контролируемого допуска. Автоматические provider retries, очистка чужих данных и использование test IdP для постоянного входа не допускаются.

## Проверка и возврат

Обязательны configuration/secret-scope checks, exact image scan, HTTPS login одного пользователя с контрактными permissions, private-only listener, readiness всех ролей и сквозная цепочка с реальными владельческими БД/Kafka/SSE. Restart должен сохранить identity и данные. До cutover сохраняются текущие image/container/volume identities; при неуспехе снимаются только созданные этим запуском ресурсы, существующие данные и telemetry volumes сохраняются.

Это решение не объявляет normal startup, login или production admission уже выполненными.
