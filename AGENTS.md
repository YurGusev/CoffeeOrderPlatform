# Руководство для агентов CoffeeOrderPlatform

Этот репозиторий содержит новую CoffeeOrderPlatform, строящуюся с нуля по
подходу «сначала микросервисы». Это не рабочая область миграции: запрещено
переносить из CoffeeOrderSystem runtime-код, модели БД, сгенерированные
артефакты и внутренние типы.

Для значимой работы выбрать навыки через `.agents/skills/coffee-platform-router/SKILL.md`.
`docs/launch/README.md` использовать как указатель на документы затронутой области;
из канонических revision roots читать документы нужных бизнес-инвариантов.
Уже прочитанное перечитывать только при изменении документа или области задачи.

В DSH `coffee-platform-router` выбирает предметные навыки проекта. Если задача
не покрыта таблицей router, сначала прочитать определяющие документы области и
только затем решать, нужен ли новый навык; не выдумывать workflow и не запускать
неподходящий навык ради формального покрытия. Маршруты для PR/гейтов, Obsidian и
DSH-плагинов также определены в router.
Загружать выбранные навыки из `.agents/skills` через `skill`; глобальные
копии не устанавливать. Если навыки не обнаружены, проверить рабочий каталог
сессии и доверие к точному корню проекта; после исправления начать новую сессию.
Исторические `AGENT_SKILLS_NEW_ARCHITECTURE` не подключать как рабочие
навыки; настройки ролей из `.codex` не переносить в DSH.

Простые задачи выполнять без делегирования. Для независимых частей использовать
`subagent` (изолированный контекст) или `subagent_fork` (наследует завершённые ходы
беседы); `workflow` — только для явно запрошенной крупной многокомпонентной
оркестрации с фазами и structured results.
Передавать ребёнку корень проекта, нужные навыки с требованием загрузить их через
`skill`, границы файлов и проверки; не поручать нескольким исполнителям одни и те
же изменения. Для одной задачи не запускать параллельно DSH-делегирование,
внешнего исполнителя через Maestro и Kanban без явного выбора другого пути
пользователем.

## Субагенты и модели

- Использовать нативные `subagent`/`subagent_fork`; `workflow` — только для явно
  запрошенной крупной многокомпонентной оркестрации.
- Разрешённые модели: `opencode-go/deepseek-v4.1-flash` и
  `opencode-go/deepseek-v4-pro`; другие модели для субагентов не использовать.
- Для обеих моделей передавать `reasoning_effort: "max"`. Root по умолчанию
  Flash/max; для сложной архитектуры, финального ревью и приёмки выбирать Pro/max.
- Flash: explorer/researcher/tester и малые локальные правки; Pro: сложная
  реализация, архитектурные решения, reviewer и merge/acceptance.
- Передавать goal, cwd, файлы/ownership, acceptance, модель/effort и формат
  результата. Ребёнок возвращает файлы/строки, команды, результаты и limitations;
  родитель проверяет вывод по файлам и фактическому tool output.
- «Только чтение» — инструкция; для технической изоляции использовать preset.
  Write-задачи выполнять последовательно или в отдельных worktrees.
- Дети не делают push, merge и закрытие issue; это остаётся root.

## Ветки и язык проекта

- GitHub `YurGusev/CoffeeOrderPlatform` — единственная operational authority для
  remote repository, issues, labels, branches, pull requests, checks, reviews,
  releases и Projects. Другой forge для этого репозитория запрещён.
- Перед remote mutation проверять `origin` и `gh repo view`; target обязан быть
  `https://github.com/YurGusev/CoffeeOrderPlatform`.
- Перед merge прочитать все комментарии и review threads ревьювера на текущем
  head; на каждое существенное замечание подготовить ответ (исправление с
  commit/evidence или обоснованный отказ) и resolve. Публикация ответа и resolve —
  remote mutation, нужно разрешение. Unresolved P0/P1 блокирует merge. После push
  перечитать head и checks; зелёные checks со старого head не считать.

- `develop` — единственная постоянная ветка разработки и база всех рабочих веток.
- `main` — стабильная/релизная линия; прямую разработку в ней не вести.
- Ветка задачи создаётся от актуальной `develop`: `feature/<issue>-<slug>`,
  `fix/<issue>-<slug>`, `docs/<issue>-<slug>` или `test/<issue>-<slug>`.
- Один issue — одна рабочая ветка и один PR в `develop`.
- Политика интеграции: в `develop` вливаются merge-коммиты; squash — только по
  отдельному решению. PR целевых и тестовых веток тоже целят в `develop`, а
  тестовая ветка получает изменения из `develop` слиянием. Промежуточная
  тест-ветка не становится вторым интеграционным пунктом: PR в неё не открываются
  (урок PR #316–#321, влитых в `test/13-launch-verification` вместо `develop`).
- Опубликованную историю (`rebase`, `push --force*`) не переписывать без
  backup-тега `backup/<branch>-<date>` (или `backup/...-pre-rebase-<date>`),
  записи прежних SHA и явного согласования владельца.
- Зелёный CI: `check` запускается только для push/PR от владельца (`YurGusev`);
  push аккаунта `coffee-platform-agent` даёт SKIPPED по guard в
  `.github/workflows/check.yml` и не считается зелёным CI. Агент подтверждает
  сборку локальным `pnpm check` под общим flock.
- Удаление локальных веток — только после архивного тега на их tip и проверки
  merged/unmerged; merged-ветки удаляются вместе с их worktree только после
  подтверждения.
- Issue, коммиты, названия и описания PR, а также изменяемая документация ведутся
  на русском языке. Технические идентификаторы, имена API, типов, событий,
  файлов и веток не переводятся.
- Каждый issue обязан содержать прямые ссылки на определяющие документы,
  конкретный перечень реализации, обязательные тесты, границы и критерии готовности.
- Документация меняется в той же ветке и том же PR, что и соответствующее поведение.

## Имена создаваемых артефактов

- Создаваемые имена — временные каталоги, git refs, bundles, файлы состояния —
  не содержат идентификаторов гейтов (`g08`, `g15`, `g18`) и их названий.
  Идентификатор гейта остаётся в данных (`gate`, `gateId`, `code`, `profile`),
  а не в имени.
- Исторические опубликованные имена остаются читаемыми: новые артефакты
  создаются только с нейтральными именами, но чтение принимает старые имена.

## Архитектурные ограничения

- Ограниченный контекст владеет своими данными, миграциями, командами, событиями и восстановлением.
- Межвладельческий SQL и общие изменяемые бизнес-сущности запрещены.
- HTTP обслуживает немедленные операции; Kafka переносит долговечные асинхронные сообщения.
- PostgreSQL остаётся источником бизнес-истины; Outbox/Inbox защищают эффекты доставки.
- Публичные, agent, internal, webhook, realtime и provider trust surfaces разделены явно.
- AROMA Gateway владеет только транспортом провайдера; Orders владеет convergence корзины.
- React использует `client-v1`, серверные состояния и `allowedActions`.
- Новая технология добавляется только ради названной гарантии, измеренного ограничения или требования провайдера.
- Все несекретные настройки читаются только из `config/platform.yaml`; все
  секреты хранятся только в encrypted `secrets/platform.secrets.sops.yaml`.
  Другие `.env`, service config и password files запрещены.
- Runtime получает только свою scoped secret materialization в tmpfs; общий
  secrets-файл может расшифровывать только trusted `config-bootstrap`.

  восстановленный #3 не подменяет незавершённые durable foundation guarantees.
- Exact pins редактируются только в `config/toolchain-versions.json`.

Работать локально в `/home/yurgusev/CoffeeOrderPlatform` и проверять изменения
до коммита. GitHub push, создание/изменение issue и PR, deployment, мутации провайдера
и production-данных требуют явного разрешения пользователя.

Канонические revision roots неизменяемы и сохраняют исходный язык и контрольные
суммы. Новые исполнимые решения оформляются на русском в обычных ADR,
контрактах и документации сервисов, инфраструктуры или первого запуска.

## Style Guide

### General Principles

- Проверять неизвестные значения один раз на владеющей ими границе. Внутрь
  передавать типизированные значения вместо повторных проверок
  `typeof value === "object"` и наличия свойств. Не проверять защитно заново
  значения, уже гарантированные схемой, конструктором или внутренним типом.
- Не выделять одноразовые helpers заранее. Оставлять логику в месте вызова,
  если helper не переиспользуется, не скрывает действительно сложную границу
  и не имеет ясного самостоятельного имени, улучшающего читаемость caller.
- По возможности избегать `try/catch`.
- Перед добавлением сложности ради спекулятивного или крайне маловероятного
  race condition либо security edge case сначала объяснить пользователю
  конкретный failure mode, вероятность и цену сложности и получить согласие.
  Не расширять scope тихо «для теоретической надёжности».

## Scope Guard: минимально достаточное изменение

Выполнять текущую задачу минимальным достаточным изменением.

### До начала правок

- Прочитать непосредственно относящиеся к задаче код, тесты и конфигурацию. Не
  принимать решения по фрагментам поисковой выдачи или догадкам.
- Если требование неоднозначно или исходное утверждение не подтверждено,
  сначала устранить неоднозначность или проверить утверждение.
- До значимых правок обозначить результат, границы, затронутые файлы и проверку.
  Для небольшого изменения достаточно короткого пояснения без отдельных разделов.
- Начать с одного пути реализации. Разделять работу только при наличии
  действительно независимых частей.

### Во время правок

- Сначала переиспользовать существующие код, helpers, patterns и test setup;
  добавлять новые только при доказанной необходимости.
- Исправлять первопричину ошибки, не наслаивать обходные патчи на неверное
  исходное предположение.
- Добавлять abstraction, adapter или config layer только при наличии второго
  реального caller в этой задаче либо прямого требования.
- Сохранять поведение вне запрошенного изменения.
- Не проектировать редкие или будущие случаи, которых нет в требованиях.
- Удалять заменённый путь. Сохранять старую и новую реализации одновременно
  только при явном требовании совместимости.

### Когда требуется пауза и подтверждение пользователя

Read-only исследование разрешено всегда. Если задача явно не дала такое
разрешение, получить подтверждение пользователя до любого из действий:

- существенно расширить scope или изменить несвязанные файлы;
- добавить dependency, framework, service или новую test infrastructure;
- изменить public API, schema, storage format или wire format;
- удалить или перезаписать пользовательские данные, отбросить uncommitted work,
  переписать git history или удалить данные из хранилища;
- оставить одновременно две реализации одного поведения.

### Тестирование

На общем self-hosted `dev-machine` native builds, полный `pnpm check`, G12,
runtime matrix, SSE qualification и полный launch используют один OS `flock`:
`${XDG_RUNTIME_DIR:-/run/user/$(id -u)}/coffee-platform-heavy.lock`.
Например, локальная команда: `flock --no-fork "${XDG_RUNTIME_DIR:-/run/user/$(id -u)}/coffee-platform-heavy.lock" pnpm check`.
Supervisor может удерживать тот же lock через `fcntl.flock`; лимит выполнения
считается после получения lock. CI отделяет ожидание до 120 минут от прежних
30 минут install/check. Узкие unit/typecheck не требуют reservation. Перед
тяжёлым запуском проверить также уже работающие legacy-команды: advisory lock
не останавливает процессы, которые его не используют. Чужие процессы не завершать.

- Запускать самый узкий существующий набор тестов, покрывающий изменённое
  поведение.
- Перечни сценариев в предметных навыках — набор для выбора по изменению и риску.
  Явно обязательные acceptance criteria и проверки проекта выполнять полностью.
- Сначала расширять наиболее подходящий существующий test, а не создавать новый
  test file.
- Добавлять тест только когда изменяемое наблюдаемое пользователем поведение не
  покрыто либо пользователь прямо запросил тест.
- Каждый новый тест обязан защищать конкретный acceptance criterion или
  regression risk.
- Не увеличивать несвязанное покрытие и не вводить test infrastructure только
  ради одной задачи.
- Успешные тесты не являются основанием для дополнительных abstractions или
  расширения scope.

### Если план начинает расти

Если план начинает включать слои «на будущее», цепочки workaround, несвязанную
очистку или тесты поведения вне требований, сократить его до исходного scope
и продолжить. Подтверждение нужно только при изменении согласованного результата,
границ или последствий; возврат к уже разрешённой задаче его не требует.

### Условия завершения

Задача завершена только когда одновременно выполнены все условия:

- запрошенное поведение работает, acceptance criteria выполнены;
- релевантные проверки прошли, точные команды и результаты сообщены;
- каждый изменённый файл необходим, diff не содержит несвязанных изменений;
- отсутствуют debug-код, backup-копии, мёртвые пути и scratch-файлы;
- assumptions, limitations и непроверенное runtime-поведение указаны прямо.
